# [데이터베이스] PostgreSQL 설계 구조
> 해당 글은 `PostgreSQL`의 동작 원리에 대해서 큰 범위에서 정리한 글입니다.

순서는 바텀업 방식으로
1. 내부 파일이 저장되어있는 형태
2. 파일을 무결하게 관리하는 방법
3. Storage Manager/Executor
4. Planner/Analyzer/Parser
5. SQL/Function/Operator/Type
6. 사용자

로 설명을 해보도록 하겠습니다.
## 1. 내부 파일이 저장되어있는 형태
Postgresql 기준 프로그램 제일 아래에 데이터가 저장되는 공간은 다음과 같습니다.
- 디스크 (영속성)
- pg 프로세스 메모리 (캐싱)
- Buffer (pg 프로세스가 확ㄱ보한 OS Shared Memory)

또한 저장되는 형태도 제각각으로 다릅니다
- 페이지 (8Kb)
  - 엔트리 인덱스
  - 튜플
    - `xmin`, `xmax`
  - LSN
- WAL segmentation (MB 단위)
   - WAL page (8Kb)

이러한 저장 영역을 기반으로 postgresql은 데이터의 상태를 무결하게 관리하게 됩니다.

## 2. 파일을 무결하게 관리하는 방법
Postgresql에서 데이터를 저장할 때 다음과 같은 요소들의 영향을 받게됩니다.
- `dirty page`: 메모리의 페이지가 데이터베이스와 동일하지 않은 상황
- `WAL`: 커밋 상태에 따라 빠르게 디스크에 저장되는 로그
- `write`/`fsync`: os에 요청을 한 후 동기화 가 되는 과정 (디스크와 pg프로세스 메모리 사이)
- `xmin`, `xmax`: 해당 튜플을 생성/무효화한 트랜잭션 id
- `buffer`: 디스크에서 가져온 또는 생성된 `WAL record`를 디스크에 쓰기 전의 데이터를 잠깐 모아두는 공간

### 트랜잭션이 수정을 하는 과정
> 어느정도 개념을 압축하여 설명하였습니다.

하나의 트랜잭션이 행을 수정할 경우 다음과 같은 작업을 하게됩니다.
1. 자신의 트랜잭션 및 스냅샷 기록
2. 스냅샷에 존재하는 행의 `xmin`, `xmax`를 확인
3. `xmax`의 Transaction 커밋 상태 또는 `abort` 확인
4. 자신의 스냅샷과 해당 버전이 맞는지 확인 후 수정
5. WAL이 빠르게 먼저 디스크에 기록됨 (+os에 쓰기 요청)
6. checkpoint 또는 walwriter을 통해서 먼저 디스크에 들어간 WAL에 대해서 메모리의 dirty page를 디스크에 써놓기

과 같은 형태이며 이렇게 작업을 하다보면 이는 즉시 디스크에 저장되는 것이 아닌 메모리에만 변경 사항이 존재할 수 있으며 이를 쓰이지 않은 데이터, `dirty page`라고 부르게됩니다.

## 3. postgres가 구성되어있는 요소
Postgresql는 내부적으로 c기반 런타임 코드로 구성되어있으며 가장 기본적인 메타데이터 저장소는 `pg_catalog`라는 Postgres의 내부 상태와 메타데이터를 SQL로 볼 수 있게 해주는 카탈로그 스키마가 존재합니다.

Postgresql은 다른 언어의 메서드/클래스 등의 메타데이터 대신 이미 사용하고 있는 구조인 테이블을 이용하여 함수, 객체, 관계, 제약 등의 메타데이터를 관리합니다.

스키마란 하나의 데이터베이스 안에 존재하는 여러 `namespace` 정도로 이해가 가능합니다.

해당 스키마에는 여러 테이블이 존재합니다.
- `pg_type`: `int64` 등과 같은 타입이 존재
- `pg_proc`: 프로시저와 함수
- `pg_class`: 테이블, 인덱스, 뷰 등과 같은 `relation`의 메타데이터
- `pg_attribute`: 컬럼 및 속성들을 저장하는 테이블
- `pg_namespace`: 스키마들을 관리하는 테이블

이외에도 Postgres에는 여러 스키마와 테이블이 존재하여 사용자 권한, 세션, 함수를 통한 데이터의 버전 확인, 확장 플러그인 관리, 의존성 등을 관리합니다.


## 4. postgres가 쿼리를 수정하는 과정
Postgres는 사용자의 요청을 받기 위해 연결된 커넥션의 세션(backend 프로세스)에 대해서 요청을 받게 됩니다. 그 세션에서는 하나 이상의 쿼리를 받아 이를 처리해주게 되는데요.

순서는 다음과 같습니다.
1. Parser: 쿼리 파싱. 처음에 들어온 문자열 쿼리를 구문 구조 `Parse Tree`로 분해하게 됩니다. (여기에서 문법 오류가 걸러지게 됩니다.)
2. Analyzer: 만들어진 트리를 기반으로 사용 객체, 받으려는 정보, 사용 연산들 등을 필요한 내용끼리 합치고 다음 단계로 보내줍니다. (여기에서 존재하지 않는 컬럼 또는 객체 타입 등에 대한 오류가 생깁니다.)
3. Rewriter: 위에서 만들어진 정의를 펼쳐서 내부적으로 필요한 규칙을 적용하여 다시 쿼리를 만들게 됩니다.
4. Planner/Optimizer: 시퀀스, 인덱스 스캔 방식 중에서 데이터 개수, 제약조건, 인덱스 여부 등을 확인하여 계산 비용을 추정한 뒤 예상 비용이 더 낮은쪽을 선택하게 됩니다. `EXPLAIN [QUERY]`를 이용하여 이 결과를 확인할 수 있습니다.
5. Executer: 최종적으로 트리구조의 실행 계획을 실행하며 `6번`에 존재하는 내용들에서 데이터를 가져오게 됩니다. 여기부터 MVCC 검사, 읽기수준, 조건문 검사, 버퍼에서 페이지 확인, 디스크 읽기, 스냅샷 비교 등을 하게 됩니다.
