# 목표 생성

## 엔드포인트

- `POST /api/goals`

## 요청 스키마

```json
{
  "goalType": "WEEKLY",
  "targetDistance": 20000,
  "startDate": "2026-09-01",
  "endDate": "2026-09-07"
}
```

## 응답 스키마

```json
{
  "success": true,
  "data": {
    "idx": 1,
    "goalType": "WEEKLY",
    "targetDistance": 20000,
    "status": "ACTIVE"
  }
}
```

## 인증/인가

- `authenticate`

## 검사하는 내용

- 목표 종류 값
- 목표 거리 양수 여부
- 시작일과 종료일이 실제 존재하는 `YYYY-MM-DD` 날짜인지 여부
- 시작일과 종료일 순서
- 만료된 기존 목표 상태 갱신 필요 여부
- 동일 사용자의 활성 목표 존재 여부

## 조회하는 상태

- 사용자 idx `[running_goals.users_idx]`
- 목표 상태 `[running_goals.status]`
- 목표 시작일 `[running_goals.start_date]`
- 목표 종료일 `[running_goals.end_date]`

## 저장/변경하는 상태

- 사용자 idx `[running_goals.users_idx]`
- 목표 종류 `[running_goals.goal_type]`
- 목표 거리 `[running_goals.target_distance]`
- 목표 상태 `[running_goals.status]`
- 시작일 `[running_goals.start_date]`
- 종료일 `[running_goals.end_date]`
- 생성 시각 `[running_goals.created_at]`

## 구현 메모

- 목표 생성 전에 `goals.service.refreshExpiredGoals(userIdx)`를 먼저 실행합니다.
- 만료 정리 후에도 `ACTIVE` 목표가 남아 있으면 새 목표 생성을 거부합니다.
- 현재 정책은 사용자당 `ACTIVE` 목표 1개입니다. `goal_type`별 1개가 아니라 전체 1개로 제한합니다.
- 시작일과 종료일은 요청값을 사용하고, 서버는 `startDate <= endDate`만 검증합니다.
- 추후 업그레이드 시 삭제할 요소: service 레벨에서만 막는 `ACTIVE` 중복 제어.
- 추후 업그레이드 시 추가할 내용: DB partial unique index로 `users_idx WHERE status='ACTIVE'` 중복 방지.
