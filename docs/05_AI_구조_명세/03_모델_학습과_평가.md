# 모델 학습과 평가

## 목표

모델이 달라도 **같은 Dataset / Split / Metric / Artifact 규격**으로 비교한다.

---

# 1. 공통 모델 계약

모든 모델은 최종적으로 Candidate마다 점수 하나를 반환해야 한다.

```python
model = create_model(model_config, ordered_feature_columns, seed)
model.fit(train_df, validation_df)
scores = model.predict_scores(candidate_df)
```

공통 규칙:

- 출력 shape = Candidate 행 수
- 모든 score는 유한한 숫자
- 높은 score가 높은 순위
- 입력 행 순서와 score 순서가 일치
- Utility / Ground Truth는 추론 입력에 필요하지 않음
- 저장 후 다시 불러와도 같은 Schema를 사용

# 2. 모델별 학습 방식

## Baseline — condition_score

```text
기존 condition_score DESC
```

학습하지 않는다.

AI가 기존 휴리스틱보다 실제로 나아졌는지 판단하기 위한 기준선이다.

## Pairwise Logistic Regression

같은 Request 안의 후보 두 개를 비교한다.

```text
Utility(A) > Utility(B)
→ Feature(A) - Feature(B)
→ A가 더 좋다는 Binary Preference 학습
```

## Random Forest

후보 하나씩 Utility 값을 회귀한다.

```text
Feature(candidate) → Utility
```

예측된 Utility 성격의 Score로 정렬한다.

## LightGBM Ranker

```text
label = relevance
group = request 단위 후보 수
objective = lambdarank 계열
```

같은 Request 안 후보의 순서를 NDCG 관점에서 개선하는 Learning to Rank 방식이다.

## XGBoost Ranker

```text
label = relevance
group = request
objective = rank:ndcg
```

## CatBoost Ranker

```text
label = relevance
group = request
loss = YetiRank 계열
```

## RankNet

후보 쌍의 상대적 선호를 Neural Network로 학습한다.

```text
score_good - score_bad
        ↓
BCEWithLogitsLoss(target=1)
```

# 3. 전처리 원칙

전처리는 **Train 데이터만으로 fit**한다.

현재 계약상 Numeric 결측은 대략 다음 방향이다.

```text
Train Median Imputation
+ Missing Indicator
+ Standardization
```

전체 Train이 결측인 컬럼은 0 처리 정책을 둔다.

Baseline `condition_score`에는 학습 전처리를 적용하지 않는다.

> Validation / Test 정보를 이용해 Median이나 Scale을 미리 계산하면 Leakage다.

---

# 4. Split — user_temporal_holdout

현재 지원하는 Split은 한 종류다.

## Cold User

일정 비율의 사용자를 Seed 기반으로 먼저 분리한다.

기본적으로 Cold 사용자는 Train / Validation에 등장하지 않는다.

```text
Cold User Requests
→ Cold Test
```

## Known User

사용자 요청을 `request_sequence` 순서대로 두고 마지막 요청들을 홀드아웃한다.

기본 개념:

```text
앞 요청들 → Train
끝에서 두 번째 → Validation
마지막 → Warm Test
```

사용자당 유효 요청이 5개라면 대표적으로:

```text
3 / 1 / 1
Train / Validation / Warm Test
```

최소 요청 수를 만족하지 못한 Known User는 `excluded` 정책에 따라 제외될 수 있다.

# 5. 평가 지표

## NDCG@K

상위 K개 Ranking의 순서 품질을 평가한다.

```text
Gain = 2^relevance - 1
Discount = log2(position)
```

현재 Ranking 품질을 보는 대표 지표다.

## Top1 Best Utility

예측 1위 후보가 해당 Request의 **최대 Utility 후보**인지 본다.

공동 최대 Utility도 정답으로 인정한다.

## Utility Regret

```text
Regret
= max_utility - predicted_top1_utility
```

낮을수록 좋다.

`0`이면 예측 1위가 Utility 기준 최적 후보라는 뜻이다.

## Pairwise Accuracy

같은 Request 안에서 Utility가 서로 다른 후보 Pair의 순서를 얼마나 맞췄는지 본다.

Utility 동점 Pair는 비교에서 제외한다.

---

# 6. Cohort

평가는 최소 다음 단위로 분리한다.

```text
Overall
Warm
Cold
```

이 구분은 중요하다.

전체 평균만 보면 기존 사용자를 잘 맞추는 모델이 신규 사용자 문제를 가릴 수 있기 때문이다.

---

# 7. 신뢰구간

반복 요청이 같은 사용자에게 묶여 있으므로 Request를 완전히 독립으로 보지 않는다.

현재 신뢰구간은 사용자 단위 **Cluster Bootstrap**으로 계산하는 방향이다.

```text
User 단위 Sample
→ 그 사용자의 Request 묶음을 함께 Sample
→ Metric 반복 계산
→ 95% CI
```

유효 사용자가 너무 적거나 bootstrap을 끄면 CI는 null일 수 있다.

---

# 8. 현재 사용하지 않는 지표

현재 실제 사용자의 `selected` 정답을 만들어내지 않으므로 다음을 억지로 계산하지 않는다.

```text
HitRate
MRR
실제 선택 Accuracy
```

실제 선택 로그가 생기면 이후 별도 평가축으로 추가하는 것이 맞다.

---

# 9. 모델 비교 시 보는 순서

추천 순서:

```text
1. Dataset / Split 동일성 확인
2. Baseline 확인
3. Overall NDCG@K
4. Warm / Cold 분리
5. Utility Regret
6. Pairwise Accuracy
7. Top1 Best Utility
8. 95% CI
9. Resource Usage
10. Feature Importance / Training History
```

숫자 하나만 보고 모델을 선택하지 않는다.

---

# 10. 모델 선택 시 최소 체크

- [ ] Baseline보다 의미 있게 좋은가
- [ ] Cold 성능이 과도하게 무너지지 않는가
- [ ] Utility Regret이 낮아지는가
- [ ] CI가 지나치게 넓지 않은가
- [ ] 추론 비용이 운영에 허용 가능한가
- [ ] 모델 저장/복원 후 결과가 유지되는가
- [ ] Export 후 독립 추론이 가능한가
- [ ] 합성 Utility를 과적합한 것뿐이라는 위험을 구분했는가
