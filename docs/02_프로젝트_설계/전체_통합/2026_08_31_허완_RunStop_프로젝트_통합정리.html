현재 상태 리뷰

지금 바꾸기보다 “확인하고 넘어갈 것”을 분리했습니다.

DB에서 확실히 정리된 것

  • 자체 로그인: login_id + password_hash, JWT/bcrypt 방향
  • 탈퇴는 행 삭제가 아니라 WITHDRAWN + login_id 익명화 + phone NULL + withdrawn_at
  • 실제 시각은 timestamptz, 목표 기간은 date
  • 전체 경로는 recommendation.route LineString, route_points는 주요 지점만
  • GPS 캐시 재전송은 client_trackpoint_id UUID UNIQUE로 중복 방지
  • route_requests / recommendation 이력은 보존

datasets에서 당장 안 건드릴 것

  • 7개 물리 테이블 구조 유지
  • 시설 Point/도로 공간 컬럼에 GiST 적용
  • parks는 현재 Point 유지, 실제 경계 데이터가 생길 때 Polygon 검토
  • pedestrian_roads는 start/end Point + 필요 시 LineString 정책 유지
  • 정제 데이터는 초기 적재 후 읽기 중심으로 사용
리뷰 게이트 1 · Migration ↔ 최신 ERD 동기화
현재 Git HEAD에는 create-schemas.js와 create-tables.js가 존재하지만, 확인한 migration의 service.users는 최신 ERD와 아직 완전히 같지 않습니다. 예: phone UNIQUE, withdrawn_at, 일부 timestamptz 정책이 최신 ERD 쪽에 더 앞서 있습니다. 따라서 상태는 “migration 구현됨”이 아니라 “초기 migration 구현 + 최신 ERD sync 확인 필요”로 보는 것이 정확합니다.
리뷰 게이트 2 · API 초안 ↔ DB 정책 동기화
기존 API 편집기에는 email, 러닝 feedback, 심박/케이던스, 문의 category, trackpoint idempotency 등 현재 DB와 맞지 않거나 미확정인 항목이 남아 있습니다. Node 구현 시작 전에 DTO를 한 번 최신 DB에 맞춰 잠그는 것이 좋습니다.
결론 · 지금은 DB를 더 늘리기보다 Node 공통 규격을 만드는 단계로 넘어가도 됩니다. 이후 DB 변경은 실제 API/알고리즘 인터페이스에서 필요성이 생길 때 작은 migration으로 추가하는 편이 좋습니다.

업로드된 dbdiagram datasets ERD 원본 참고 이미지

사용자 중심

  • users → user_profiles (1:1)
  • users → running_goals / bookmarks / sessions / inquiries
  • 탈퇴해도 users 행을 유지해 FK 이력을 보존

경로 추천 중심

  • route_requests → request_points (1:N)
  • route_requests → recommendations (1:N)
  • route_requests.selected_recommendations_idx → 최종 선택 후보
  • recommendation → route_points / bookmarks / running_sessions

러닝 추적

  • running_sessions → running_trackpoints (1:N)
  • trackpoint는 클라이언트 UUID로 재전송 멱등성 확보
  • 평균 페이스/거리 등은 session 요약값으로 집계

공간 데이터

  • service: 사용자/경로/GPS geometry
  • datasets: 읽기 중심 시설/환경 geometry
  • EPSG:4326 저장 · 거리/Buffer 계산 시 필요하면 5179 변환

Figma metadata에서 디자인 프레임이 존재하는 것은 확인했지만, 이것만으로 React Native 코드 구현 완료를 의미하지는 않습니다.

Python Worker와 Node의 경계

  • FastAPI 런타임과 /health 골격은 준비된 상태
  • 경로 생성 · Feature · Ranking · AI inference는 알고리즘 구현 영역
  • Node에서는 알고리즘 내부를 기다리지 말고 WorkerAdapter JSON contract를 먼저 고정
  • timeout / unavailable / invalid response를 Node 공통 오류로 변환
즉, 현재 서버 작업은 Python 알고리즘과 병렬로 진행할 수 있습니다.
