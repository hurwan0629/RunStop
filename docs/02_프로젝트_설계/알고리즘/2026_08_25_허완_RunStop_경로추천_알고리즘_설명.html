RunStop · 경로 추천 알고리즘 1안

“핵심 지점만 정하고, 그 사이의 실제 도로 후보를 만든 뒤 전체 코스를 다시 평가한다.”

이 문서는 RunStop의 경로 추천 흐름을 이해하기 쉽게 풀어쓴 설명이다. 핵심은 모든 도로 노드를 미리 선택하지 않는 것이다. 먼저 소수의 핵심 경유지(Waypoint)를 정하고, 각 경유지 사이를 실제 보행 도로 그래프에서 탐색한 뒤, 여러 구간 후보를 조합해 하나의 순환 러닝 코스를 만든다.

가장 중요한 구분
Dijkstra는 “완성된 코스 3개 중 1등을 고르는 알고리즘”이 아니라, 한 지점에서 다른 지점까지 실제 도로를 따라 Cost가 낮은 경로를 찾는 알고리즘이다. 완성된 러닝 코스의 최종 순위는 별도의 Route Score로 결정한다.

전체 알고리즘 구조

사용자 요구 분리필수 조건, 선호 조건, 근접 조건으로 나눈다.
검색 영역 제한목표 거리를 이용해 출발지 주변의 탐색 영역을 줄인다.
실제 보행 도로 그래프 준비Node와 Edge, 그리고 각 Edge의 실제 도로 geometry를 사용한다.
Edge에 환경 데이터 결합거리, 경사, 가로등, CCTV, 보행자도로 여부 등을 붙인다.
핵심 Waypoint 후보 생성Start → W1 → W2 → … → Start 구조의 핵심 지점을 정한다.
Waypoint 사이 경로 후보 생성Dijkstra / A* / K-Shortest Path 등으로 각 구간의 실제 도로 후보를 만든다.
구간 후보 Top K 유지구간별 1등 하나만 확정하지 않고 유망한 후보 몇 개를 남긴다.
전체 순환 경로 조합각 구간 후보들을 이어 여러 개의 완성 코스를 만든다.
Route Feature 계산총 거리, 평균/최대 경사, 누적 상승, 시설 접근성 등을 다시 계산한다.
최종 Route Score 계산완성된 코스와 사용자 요구를 비교해 점수를 만든다.
필수 조건 재검증거리 오차, 경사 제한, 필수 경유지 등 조건을 다시 검사한다.
Top 3 반환조건을 통과한 경로 중 서로 너무 겹치지 않는 상위 3개를 추천한다.

먼저 알아야 할 핵심 용어

Node

도로 그래프의 점. 교차로, 도로가 갈라지는 지점, 도로 끝점 등을 의미한다.

Edge

Node와 Node 사이의 실제 도로 구간. 길이, 경사, 가로등 수 등의 정보를 가질 수 있다.

Waypoint

러닝 코스를 만들기 위해 의도적으로 선택하는 핵심 경유지. 모든 Node가 Waypoint가 되는 것은 아니다.

Geometry

실제 도로의 모양을 이루는 위도·경도 좌표 배열. 단순 직선이 아니라 실제 길이 휘어진 모양을 표현한다.

Edge Cost

Dijkstra가 사용할 도로 한 조각의 비용. 낮을수록 그 도로를 선택하기 좋은 것으로 정의할 수 있다.

Route Score

완성된 러닝 코스 전체에 대한 점수. 높을수록 사용자의 요구에 잘 맞는 코스로 정의한다.

1. 사용자 요구를 세 종류로 분리한다

모든 조건을 한 번에 점수로 처리하면 이상한 결과가 나올 수 있으므로 먼저 성격을 나눈다.

Hard Constraint

필수 조건

반드시 만족해야 하며, 만족하지 못하면 후보에서 제외한다.

예: 5km ± 500m, 보행 가능한 도로, 특정 지점 필수 통과

Soft Preference

선호 조건

만족할수록 점수를 높인다.

예: 경사가 낮음, 가로등 많음, 하천 근처, 녹지 많음

Near Constraint

근접 조건

정확히 통과할 필요는 없지만 일정 거리 안에 존재하면 좋다.

예: 2.5km 지점 근처에 화장실, 경로 100m 안에 편의점

2. 도로 전체를 탐색하지 않고 검색 영역을 먼저 줄인다

서울 전체 도로를 대상으로 가능한 모든 순환 경로를 만들면 경우의 수가 지나치게 커진다. 따라서 사용자의 목표 거리와 출발지를 기준으로 먼저 검색 영역을 제한한다.

예를 들어 목표가 5km 순환 코스라면 출발지 주변 몇 km 범위만 우선 가져온다. 정확한 검색 반경은 구현 단계에서 목표 거리, 도로 밀도, 허용 오차 등을 기준으로 조정할 수 있다.

이 단계의 목적은 “5km를 달리는데 전혀 필요하지 않은 먼 지역의 도로 Node와 Edge를 계산에서 제거하는 것”이다.

3. 실제 도로를 Graph로 표현한다

위도·경도 두 점을 직선으로 연결해서 경로를 만들면 건물, 강, 담장 등을 가로지를 수 있다. 따라서 경로는 처음부터 실제 보행 가능한 도로 그래프를 따라 만들어야 한다.

Node A │ │ Edge 1 : 실제 보행 도로 │ Node B │ │ Edge 2 │ Node C

Edge가 실제 geometry를 가진다는 뜻

Edge #100
from_node = 23
to_node   = 41

geometry = [
    (37.5000, 127.0100),
    (37.5002, 127.0103),
    (37.5007, 127.0105),
    (37.5011, 127.0112),
    ...
]

최종 경로가 결정되면 선택된 Edge들의 geometry를 순서대로 이어 실제 지도에 그릴 수 있다. 따라서 지도에는 단순한 직선이 아니라 실제 도로를 따라가는 선이 표시된다.

보행자전용도로 데이터는 매우 유용하지만, 그것만으로 서울 전체의 완전한 보행 도로 그래프가 만들어지는지는 별도 검증이 필요하다. 실제 구현에서는 기본 도로망 데이터와 공공데이터의 역할을 나누는 설계가 필요하다.

4. 각 Edge에 환경 데이터를 결합한다

도로 그래프만 있으면 단순 최단거리 계산밖에 할 수 없다. RunStop은 각 도로 Edge에 공공데이터에서 얻은 특징을 붙여 “어떤 길이 사용자에게 더 적합한가”를 계산한다.

Feature설명활용 예
length도로 구간 길이목표 거리, 거리 비용
avg_slope구간 평균 경사평지 선호
max_slope구간 최대 경사급경사 회피
lamp_count주변 가로등 수야간 밝기 판단
cctv_count주변 CCTV 수야간 인프라 참고
pedestrian보행자전용도로 여부보행 환경 선호
river_distance하천과 거리하천 근처 선호
green_score녹지 관련 값환경 선호

Point 데이터는 어떻게 Edge에 붙이나?

가로등이나 CCTV는 점(Point) 형태의 좌표 데이터일 가능성이 높다. 도로 Edge 주변 일정 거리의 Buffer를 만들고 그 안에 들어오는 Point를 찾는 방식으로 결합할 수 있다. 

도로 Edge 주변 30m Buffer 생성
        ↓
Buffer 안의 가로등 Point 검색
        ↓
lamp_count = 4

Buffer 안의 CCTV Point 검색
        ↓
cctv_count = 1

경사도

도로의 길이와 고도 변화량을 이용하여 구간 경사를 계산한다.

grade = (끝 고도 - 시작 고도) / 수평 거리

전체 코스에서는 평균 경사 하나만 보지 않고 최대 경사와 누적 상승 고도를 함께 계산하는 것이 좋다. 평균 경사가 같아도 중간에 매우 가파른 오르막이 있는 경로가 존재할 수 있기 때문이다.

5. 모든 Node를 찍지 않고 핵심 Waypoint만 뽑는다

전체 경로의 모든 교차로를 미리 결정하면 사실상 경로를 직접 만드는 것이므로 경우의 수가 커지고 Dijkstra의 역할도 줄어든다. 대신 전체 코스의 방향을 결정할 소수의 핵심 지점만 선택한다.

Start ↓ W1 후보: W1-A / W1-B / W1-C ↓ W2 후보: W2-A / W2-B / W2-C ↓ Start

Waypoint 선정에는 다음 요소를 사용할 수 있다.

목표 거리 진행 방향 필수 경유지 공원 하천 녹지 보행자도로 환경 선호
“한강공원을 반드시 지나가고 싶다”는 조건이면 실제 보행 도로와 연결되는 지점을 필수 Waypoint로 둘 수 있다. 반대로 “화장실이 근처에 있었으면 좋겠다”는 조건은 Waypoint로 강제하기보다 최종 Route에서 접근 거리를 평가하는 편이 자연스럽다.

6. Start-W1 사이에서도 여러 실제 도로 후보를 만든다

핵심 지점이 Start → W1 → W2 → Start로 정해졌다고 해도, 각 구간을 연결하는 실제 도로는 하나가 아닐 수 있다.

Start → W1 ├─ A1 ├─ A2 └─ A3 W1 → W2 ├─ B1 ├─ B2 └─ B3 W2 → Start ├─ C1 ├─ C2 └─ C3

이때 모든 가능한 단순 경로를 전부 생성하면 경우의 수가 크게 늘어나므로, 각 구간에서 Cost가 낮은 상위 K개 정도만 후보로 유지하는 방향이 현실적이다.

일반적인 Dijkstra는 최적 경로 1개를 찾는다. 여러 개의 후보가 필요하다면 K-Shortest Path, Yen's Algorithm, Dijkstra 반복 + 기존 경로 패널티 같은 방법을 고려할 수 있다.

7. Dijkstra가 사용할 Edge Cost를 만든다

일반적인 최단거리 Dijkstra는 Edge Cost를 단순히 거리로 둔다. RunStop에서는 사용자의 선호에 따라 도로 한 조각의 Cost를 바꿀 수 있다.

Edge Cost = 거리 비용 + 경사 비용 + 야간 환경 비용 + 보행 환경 비용 + ...

단, 길이는 m, 경사는 %, 가로등은 개수처럼 단위가 다르므로 그대로 더하면 안 된다. 먼저 각 값을 0~1 범위 등으로 정규화하고 가중치를 곱한다. 

distance_cost = 0.30
slope_cost    = 0.70
darkness_cost = 0.20

사용자 가중치:
distance_weight = 0.20
slope_weight    = 0.50
light_weight    = 0.30

edge_cost =
    0.20 * distance_cost
  + 0.50 * slope_cost
  + 0.30 * darkness_cost

이 경우 거리가 조금 더 길어도 훨씬 평탄하고 밝은 도로가 있다면 Dijkstra가 그 도로를 선택할 수 있다.

8. 구간별 1등을 바로 확정하지 않고 전체 코스를 조합한다

구간별 최적 경로를 하나씩 바로 고르면 전체 코스에서는 오히려 좋지 않을 수 있다.

구간 후보길이구간 평가
A11.3km매우 좋음
A21.5km조금 낮음

하지만 목표 거리가 5km라면 다음처럼 전체 결과가 달라질 수 있다.

A1 + B1 + C1 = 4.2km  → 목표 거리에서 너무 짧음
A2 + B2 + C1 = 5.05km → 전체적으로 더 적합

따라서 각 구간에서 상위 K개 후보를 남기고, 그 후보를 조합하여 여러 개의 완성 순환 경로를 만든 다음 다시 평가하는 구조가 필요하다.

9. 완성된 코스에서 Route Feature를 다시 계산한다

Edge Feature는 도로 한 조각의 정보이고, Route Feature는 하나의 러닝 코스 전체를 평가하기 위한 정보다.

Route Feature의미
총 거리완성 코스의 전체 길이
목표 거리 오차사용자가 원하는 거리와의 차이
평균 경사전체 구간의 평균적인 경사 수준
최대 경사가장 가파른 구간의 경사
누적 상승 고도오르막에서 상승한 고도의 합
가로등/km거리 대비 야간 인프라 밀도
화장실 수 / 위치단순 개수뿐 아니라 원하는 진행 지점 근처 존재 여부
편의점 수 / 위치경로 주변 접근성
보행자도로 비율전체 경로 중 보행자전용도로가 차지하는 비율
하천·녹지 인접 비율환경적 선호를 평가하는 값

예: “2.5km 부근에 화장실”

화장실은 Edge Cost에 무조건 넣기보다 완성된 Route에서 검사하는 편이 좋다. 사용자가 원하는 것은 “어떤 Edge에 화장실이 있느냐”가 아니라 “러닝 중 원하는 시점에 접근 가능한 화장실이 있느냐”이기 때문이다. 

사용자 요구:
약 2.5km 지점에 화장실

Route A:
2.4km 지점에서 화장실까지 60m → 높은 점수

Route B:
3.8km 지점에서 화장실까지 80m → 낮은 점수

Route C:
화장실 없음 → 0점 또는 조건에 따라 탈락

10. Route Score는 완성 코스의 최종 추천 점수다

Dijkstra가 사용하는 Edge Cost와 최종 Route Score는 목적이 다르다.

Edge Cost

질문: “이 도로 조각을 선택할 가치가 있는가?”

사용 시점: 경로 탐색 중

방향: 낮을수록 좋게 정의 가능

Route Score

질문: “완성된 이 러닝 코스가 사용자에게 얼마나 좋은가?”

사용 시점: 전체 코스 생성 후

방향: 높을수록 좋게 정의 가능

route_score =
    0.20 * distance_score
  + 0.30 * slope_score
  + 0.25 * lighting_score
  + 0.10 * toilet_score
  + 0.15 * pedestrian_score

화장실처럼 일정 개수 이상부터 효용이 거의 증가하지 않는 요소는 상한을 두는 것이 자연스럽다. 

화장실 점수 예:
0개 → 0.0
1개 → 0.8
2개 → 1.0
3개 → 1.0

11. 최종 점수가 높아도 필수 조건을 다시 검사한다

후보가 완성된 뒤에는 반드시 Hard Constraint를 다시 확인한다.

통과 예

목표 5km ± 500m

Route A = 5.2km → 통과

Route B = 4.8km → 통과

탈락 예

Route C = 6.7km → 거리 오차 초과

보행 불가능 Edge 포함 → 탈락

필수 Waypoint 미통과 → 탈락

조건을 만족하는 후보가 없으면 억지로 3개를 반환하지 않는다. “현재 조건으로 추천 가능한 경로가 없음”을 반환하고, 필요하면 거리 허용 범위나 시설 조건을 어느 정도 완화하면 가능한지 안내하는 방향이 좋다.

마지막으로 지나치게 겹치는 코스는 제거하여 Top 3가 사실상 같은 경로가 되는 문제를 줄인다.

12. AI는 어디에 적용할 수 있는가?

그래프 탐색 자체는 기존 알고리즘이 안정적이므로, AI는 “어떤 도로와 경로가 사용자에게 더 좋은가”를 학습하는 쪽이 명확하다.

초기에는 사람이 정의한 점수로 충분히 시작할 수 있다. 이후 사용자 선택 데이터가 쌓이면 Route Ranking부터 AI로 대체하는 방식이 가장 자연스럽다.

예시: “5km, 평지 위주, 밤에 밝고 2.5km쯤 화장실”

요구 분리5km ± 허용오차는 Hard, 평지·밝기는 Soft, 2.5km 화장실은 Near 조건으로 분리한다.
영역 제한출발지 주변에서 5km 순환 코스를 만들 수 있는 범위의 보행 도로만 가져온다.
Edge Feature 생성각 도로에 거리, 경사, 가로등 밀도 등을 붙인다.
Waypoint 후보 생성5km 순환이 가능하도록 W1, W2 후보를 몇 개 선정한다.
각 구간 후보 탐색Start-W1, W1-W2, W2-Start에서 낮은 Edge Cost를 가진 실제 도로 후보를 몇 개 만든다.
전체 코스 조합A1+B2+C1 같은 여러 순환 코스를 만든다.
Route Feature 계산총 거리, 평균/최대 경사, 누적 상승, 가로등/km, 화장실 위치를 계산한다.
최종 평가거리 허용범위를 통과한 후보 중 경사가 낮고 밝으며 2.5km 부근 화장실 접근성이 높은 경로에 높은 점수를 준다.
Top 3 반환서로 너무 비슷한 코스를 제거하고 최종 3개를 제시한다.

전체 흐름 의사코드

function recommend_route(user_request):

    hard, soft, near = parse_user_request(user_request)

    search_area = calculate_search_area(
        start = user_request.start,
        target_distance = user_request.distance
    )

    graph = load_walking_graph(search_area)


    # 1. Edge Feature 생성
    for edge in graph.edges:

        edge.length = calculate_length(edge)

        edge.avg_slope = calculate_avg_slope(edge)
        edge.max_slope = calculate_max_slope(edge)

        edge.lamp_count = count_lamps_near(edge)
        edge.cctv_count = count_cctv_near(edge)

        edge.pedestrian = check_pedestrian_road(edge)

        edge.environment = calculate_environment_features(edge)


    # 2. 사용자의 선호를 반영한 Edge Cost 계산
    for edge in graph.edges:

        edge.cost = calculate_edge_cost(
            edge,
            soft
        )


    # 3. 핵심 Waypoint 후보 생성
    waypoint_sets = generate_waypoint_candidates(
        graph,
        user_request,
        hard,
        soft
    )


    route_candidates = []


    # 4. Waypoint 사이의 경로 후보 생성
    for waypoint_set in waypoint_sets:

        points = [
            start,
            W1,
            W2,
            ...,
            start
        ]

        segment_groups = []

        for point_a, point_b in consecutive(points):

            segment_paths = find_k_best_paths(
                graph,
                point_a,
                point_b,
                edge_cost
            )

            segment_groups.append(segment_paths)


        # 5. 구간 후보를 조합해 전체 순환 Route 생성
        routes = combine_segment_candidates(segment_groups)

        route_candidates.extend(routes)


    valid_routes = []


    # 6. 전체 Route 평가
    for route in route_candidates:

        features = calculate_route_features(route)

        if not satisfies_hard_conditions(
            route,
            features,
            hard
        ):
            continue


        near_score = evaluate_near_conditions(
            route,
            near
        )


        route.score = calculate_route_score(
            features,
            soft,
            near_score
        )


        valid_routes.append(route)


    if valid_routes is empty:
        return NO_ROUTE


    # 7. 점수순 정렬 및 중복 경로 제거
    valid_routes = sort_by_score(valid_routes)

    valid_routes = remove_highly_overlapping_routes(
        valid_routes
    )


    return valid_routes[:3]

실제 서비스 전체를 한 번에 구현하기보다 작은 도로 그래프를 직접 만들어 distance + slope + lighting만 Edge Cost로 넣고 Dijkstra 결과가 사용자 선호에 따라 어떻게 달라지는지 확인하는 것이 좋다. 이후 K개의 후보, Route Feature, 전체 Ranking 순서로 확장하면 이해하기 쉽다.
