# RunStop 러닝 코스 추천 알고리즘 설계

## 1. 개요

RunStop은 TMAP 보행자 경로 API를 통해 실제 보행 가능한 후보 경로를 생성하고, 각 경로 주변의 공공데이터를 분석하여 사용자의 러닝 조건에 적합한 코스를 추천한다.

주요 활용 데이터는 다음과 같다.

- 공중화장실정보
- 편의점 시설정보
- 도시공원정보
- 스마트가로등정보
- CCTV정보
- 고도 및 경사정보

무료 Wi-Fi와 자전거보관소 데이터는 추천 점수의 핵심 요소보다는 부가정보로 활용한다.

## 3. 컴포넌트 간 데이터 형식 및 연결 규칙

RunStop은 하나의 알고리즘만으로 동작하는 서비스가 아니라 다음과 같은 여러 컴포넌트가 연결되어 동작한다.

```text
모바일 앱
↓
RunStop Backend
↓
TMAP API
↓
경로 알고리즘
↓
공간 데이터
↓
점수 계산
↓
AI / LLM
↓
모바일 앱
```

각 컴포넌트는 서로 사용하는 데이터 형식이 다를 수 있기 때문에, 중간 단계에서 데이터 변환이 필요하다.

이 과정에서 형식이 일치하지 않으면 경로 계산 오류, 좌표 위치 오류, Feature 계산 오류 등이 발생할 수 있다.

따라서 RunStop에서는 컴포넌트 간 주고받는 데이터 형식을 미리 통일하여 사용한다.

---

### 3.1 주요 충돌 지점

RunStop에서 예상되는 주요 데이터 충돌 지점은 다음과 같다.

| 구간 | 발생 가능한 문제 |
|---|---|
| 모바일 앱 → Backend | 필드명, 타입, 필수값 불일치 |
| Backend → TMAP | 위도/경도 순서 오류 |
| TMAP → Backend | 경로 좌표 구조 변환 필요 |
| Backend → 공간데이터 | 좌표계 불일치 |
| 공간데이터 → 알고리즘 | Point / LineString / Polygon 형식 차이 |
| 알고리즘 → AI | 숫자 Feature와 자연어 입력 형식 차이 |
| AI → Backend | 자유로운 자연어 출력으로 인한 구조 불일치 |

---

### 3.2 좌표 형식 통일

RunStop에서 외부 API와 모바일 앱이 사용하는 기본 좌표 형식은 다음과 같이 통일한다.

```json
{
  "latitude": 37.543,
  "longitude": 127.044
}
```

기본 좌표계는 다음을 사용한다.

```text
WGS84
EPSG:4326
```

내부 공간 분석 과정에서는 실제 거리 계산을 위해 다음 좌표계로 변환한다.

```text
EPSG:4326
↓
EPSG:5179
```

원칙:

```text
외부 통신
→ EPSG:4326

거리 / Buffer / 공간 분석
→ EPSG:5179
```

---

### 3.3 위도와 경도 순서 통일

서비스 내부 JSON에서는 다음 순서를 사용한다.

```text
latitude
longitude
```

예:

```json
{
  "latitude": 37.543,
  "longitude": 127.044
}
```

하지만 GIS 라이브러리에서 좌표를 생성할 때는 일반적으로 다음 순서를 사용한다.

```text
longitude
latitude
```

예:

```python
Point(longitude, latitude)
```

따라서 다음과 같은 변환 규칙을 명확히 한다.

```text
API / JSON

latitude, longitude

↓

GIS

longitude, latitude
```

위도와 경도가 바뀌는 경우 전혀 다른 위치에 좌표가 표시될 수 있으므로 가장 중요한 검증 항목 중 하나이다.

---

### 3.4 TMAP 경로 응답 통일

TMAP에서 반환된 경로 좌표는 RunStop 내부에서 공통적인 형태로 변환한다.

예:

```json
{
  "routeId": 101,
  "coordinates": [
    {
      "latitude": 37.5430,
      "longitude": 127.0440
    },
    {
      "latitude": 37.5432,
      "longitude": 127.0445
    }
  ]
}
```

공간 분석 단계에서는 위 데이터를 `LineString`으로 변환한다.

```text
TMAP 경로 좌표

↓

공통 Coordinate 배열

↓

LineString

↓

Buffer / 거리 / 공간분석
```

이를 통해 이후 화장실, 편의점, 공원, 가로등, CCTV 분석에서 동일한 경로 객체를 사용할 수 있다.

---

### 3.5 공간 데이터 형식 통일

공공데이터마다 구조가 다르기 때문에 공통 필드를 정의한다.

최소 공통 필드:

```text
id
name
latitude
longitude
geometry
data_type
```

예:

```json
{
  "id": "TOILET_001",
  "name": "서울숲 공중화장실",
  "latitude": 37.543,
  "longitude": 127.044,
  "dataType": "TOILET"
}
```

시설 종류에 따라 추가 필드를 사용할 수 있다.

예:

```text
화장실
- 운영시간

공원
- 면적
- 공원유형

가로등
- 설치상태

CCTV
- 설치목적
```

---

### 3.6 공간 객체 형식 차이

RunStop에서 사용하는 공간 데이터는 크게 다음 세 가지 형태로 구분된다.

```text
Point
LineString
Polygon
```

예:

```text
화장실
편의점
가로등
CCTV
→ Point

러닝 코스
→ LineString

공원 경계
→ Polygon
```

각 데이터 형식에 따라 분석 방식도 달라진다.

```text
Point ↔ LineString
→ 시설과 코스 사이 거리 계산

Polygon ↔ LineString
→ 코스가 해당 영역을 통과하는 비율 계산
```

따라서 공간데이터를 알고리즘에 전달할 때 데이터 유형을 명확히 관리한다.

---

### 3.7 Feature 데이터 형식 통일

공간 분석 결과는 최종적으로 Feature 객체 하나로 통일한다.

예:

```json
{
  "routeId": 101,
  "features": {
    "distanceKm": 7.1,
    "distanceError": 0.014,
    "toiletCount": 2,
    "toiletScore": 90,
    "storeCount": 3,
    "storeScore": 85,
    "parkScore": 76,
    "streetlightScore": 92,
    "cctvScore": 78,
    "elevationGain": 34,
    "elevationScore": 88
  }
}
```

이 구조를 기반으로 최종 점수를 계산한다.

```text
공간데이터

↓

Feature 추출

↓

Feature Object

↓

정규화

↓

가중치 적용

↓

Final Score
```

### 3.8 AI / LLM 입력 형식

LLM이 코스 자체를 생성하거나 직접 점수를 결정하지 않도록 한다.

LLM의 주요 역할은 사용자 자연어 조건을 구조화하는 것이다.

예:

사용자 입력:

```text
7km 정도 달리고 싶고
오르막은 적었으면 좋겠어.
화장실은 꼭 있었으면 좋겠어.
```

LLM 출력:

```json
{
  "targetDistanceKm": 7,
  "slopePreference": "LOW",
  "requirements": {
    "toilet": true
  }
}
```

LLM 출력은 반드시 JSON Schema 또는 사전에 정의한 구조에 맞게 반환하도록 한다.

자유로운 문자열 응답을 그대로 추천 알고리즘에 전달하지 않는다.

```text
사용자 자연어

↓

LLM

↓

구조화 JSON

↓

Backend 검증

↓

추천 알고리즘
```

---

### 3.9 AI 출력 검증

LLM의 결과는 항상 서버에서 다시 검증한다.

예:

```text
targetDistanceKm

정상:
3 ~ 30

오류:
-5
1000
문자열
```

가중치:

```text
정상:
1 ~ 5
```

허용되지 않은 값이 들어오는 경우 기본값을 사용하거나 사용자에게 재입력을 요청한다.

즉 AI 출력은 최종 데이터가 아니라 입력 보조 데이터로 사용한다.

### 3.11 예상 병목 지점

컴포넌트 연결뿐만 아니라 처리속도에서도 병목이 발생할 수 있다.

특히 다음 부분을 주의한다.

#### TMAP API 반복 호출

후보 경로를 많이 생성할수록 TMAP API 호출 횟수가 증가한다.

```text
후보 5개
→ TMAP 5회

후보 30개
→ TMAP 30회
```

따라서 무작정 많은 후보를 생성하지 않고 적절한 후보 개수를 설정한다.

---

#### 대용량 공간데이터 검색

서울 전체 가로등이나 CCTV 데이터를 모든 경로마다 전부 비교하면 연산량이 증가한다.

예:

```text
후보 경로 20개
×
가로등 수만 개
×
CCTV 수만 개
```

이 방식은 비효율적이다.

따라서 먼저 경로 주변 Bounding Box 또는 Buffer 영역에 포함되는 데이터만 조회한 뒤 계산한다.

```text
전체 공간데이터

↓

경로 주변 영역 1차 필터

↓

해당 시설만 거리 계산
```

---

#### 좌표계 반복 변환

추천 요청마다 모든 공공데이터를 EPSG:4326에서 EPSG:5179로 다시 변환하지 않는다.

서비스 시작 전 또는 데이터 적재 시 미리 변환하여 저장한다.

```text
공공데이터 수집

↓

좌표 검증

↓

EPSG:5179 변환

↓

DB 저장

↓

추천 시 바로 사용
```

---

#### AI API 호출

LLM을 추천 후보마다 반복 호출하지 않는다.

잘못된 예:

```text
코스 A
→ LLM

코스 B
→ LLM

코스 C
→ LLM
```

권장 방식:

```text
사용자 입력

↓

LLM 1회

↓

구조화 조건 생성

↓

모든 후보 경로에 동일 조건 적용
```

이를 통해 응답시간과 API 비용을 줄인다.

### 3.13 핵심 설계 원칙

1. 컴포넌트마다 직접 다른 데이터 형식을 사용하지 않는다.

2. Backend 내부에 RunStop 공통 데이터 형식을 정의한다.

3. TMAP 응답은 공통 Route 형식으로 변환한 뒤 사용한다.

4. 모든 좌표의 기본 좌표계와 위도·경도 순서를 명확하게 정의한다.

5. 공간 분석 시 Point, LineString, Polygon을 구분한다.

6. AI의 자연어 출력은 직접 사용하지 않고 구조화된 JSON으로 변환한다.

7. AI 결과는 반드시 Backend에서 검증한다.

8. 모든 추천 Feature는 하나의 Feature Object 형태로 통일한다.

9. 외부 API별 데이터 형식 변경이 전체 알고리즘에 영향을 주지 않도록 Adapter 계층을 둔다.

10. 대용량 공간데이터는 전체 검색하지 않고 경로 주변 데이터만 우선 필터링한다.

## 4. 후보 경로 생성

RunStop이 직접 도로를 생성하지 않는다.

TMAP 보행자 경로 API를 이용하여 실제 보행 가능한 경로를 생성한다.

후보 경유지를 서로 다르게 설정하여 여러 개의 후보 경로를 생성한다.

예:

```text
후보 A

출발지
→ 경유지 A
→ 경유지 B
→ 목적지


후보 B

출발지
→ 경유지 C
→ 경유지 D
→ 목적지
```

각 후보 경로는 이후 RunStop 알고리즘에서 평가한다.

## 5. Hard Constraint와 Soft Constraint

사용자가 선택한 조건을 필수조건과 선호조건으로 구분한다.

### Hard Constraint

반드시 만족해야 하는 조건이다.

예:

```text
목표 거리
7km ± 10%

화장실
최소 1곳
```

### Soft Constraint

조건을 만족할수록 높은 점수를 부여한다.

예:

```text
경사도
편의점
공원
가로등
CCTV
```

처리 과정:

```text
후보 경로

↓

Hard Constraint 검사

↓

통과한 경로

↓

Soft Constraint 점수 계산

↓

최종 Ranking
```

Hard Constraint를 모두 만족하는 코스가 없는 경우 오류를 반환하지 않는다.

대신 조건에 가장 가까운 코스를 대안으로 제공한다.

---

## 6. 거리 적합도

사용자의 목표 거리와 실제 코스 거리의 차이를 평가한다.

예:

```text
목표 거리
7km

후보 A
7.1km

후보 B
6.8km

후보 C
8.2km
```

목표 거리와 가까울수록 높은 점수를 부여한다.

거리 점수는 최종적으로 0~100점으로 변환한다.

---

## 7. 화장실 점수

화장실은 다음 요소를 평가한다.

```text
화장실 개수
+
코스에서 화장실까지 거리
+
운영시간
```

예:

```text
코스 A

화장실 2곳

32m
85m
```

코스에서 가까운 화장실일수록 높은 점수를 부여한다.

기본 거리 기준:

| 거리 | 가중치 |
|---|---:|
| 0~50m | 1.0 |
| 50~100m | 0.8 |
| 100~200m | 0.4 |
| 200m 초과 | 0 |

운영시간 정보가 존재하는 경우 현재 시간에 이용할 수 없는 화장실은 점수에서 제외한다.

---

## 8. 편의점 점수

편의점도 화장실과 동일하게 코스 접근거리를 기반으로 계산한다.

주요 Feature:

```text
편의점 개수
가장 가까운 편의점 거리
편의점/km
편의점 접근성
```

편의점 수가 많다고 점수가 계속 상승하지 않도록 최대 점수를 제한한다.

예:

```text
0개
→ 낮은 점수

1개
→ 이용 가능

2~3개
→ 높은 점수

3개 이상
→ 최대점수
```

## 9. 공원 점수

가능하면 단순 공원 개수보다 전체 러닝 코스 중 공원과 인접하는 구간의 비율을 사용한다.

예:

```text
전체 코스
7km

공원 인접 구간
2.8km

공원 인접률
40%
```

공원 Polygon 데이터를 확보하지 못한 경우 공원 대표 위경도를 이용하여 코스와 공원의 거리를 계산한다.

## 10. 가로등 점수

가로등은 다음 두 가지를 사용한다.

```text
가로등 밀도
+
가로등 커버리지
```

가로등 밀도:

```text
가로등 개수 / 코스 거리(km)
```

예:

```text
7km 코스
가로등 42개

42 / 7
= 6개/km
```

가로등이 특정 지역에 몰려 있는 문제를 해결하기 위해 코스 전체 중 가로등 인접 구간 비율도 계산한다.

서비스에서는 이를 실제 안전도로 표현하지 않고 다음과 같이 표시한다.

```text
야간 조명 인프라 높음
```

---

## 11. CCTV 점수

CCTV는 다음 값을 이용한다.

```text
CCTV 개수
CCTV/km
CCTV 인접 구간 비율
```

CCTV가 많다고 해서 실제 범죄 안전성이 높다고 판단하지 않는다.

화면에서는 다음과 같이 표현한다.

```text
안전도 90점 X

CCTV·야간 인프라 수준 높음 O
```

## 12. 고도 및 경사도 점수

러닝 코스 평가에는 다음 요소를 사용한다.

```text
누적 상승고도
1km당 상승고도
평균 경사도
최대 경사도
```

사용자가 평탄한 코스를 선호할 경우 상승고도와 경사가 낮은 코스에 높은 점수를 부여한다.

예:

```text
코스 A
누적 상승고도 35m

코스 B
누적 상승고도 85m

코스 C
누적 상승고도 150m
```

평탄한 코스 선호 사용자의 경우:

```text
A > B > C
```

순으로 평가한다.

## 14. 거리당 데이터 변환

코스 길이가 서로 다르기 때문에 시설 개수를 그대로 비교하지 않는다.

예:

```text
코스 A
5km
가로등 30개

코스 B
10km
가로등 40개
```

단순 개수:

```text
B > A
```

거리당 계산:

```text
A
6개/km

B
4개/km
```

따라서 다음 데이터를 거리당 값으로 변환한다.

```text
화장실/km
편의점/km
가로등/km
CCTV/km
```

## 15. 점수 정규화

모든 Feature는 단위가 다르기 때문에 최종적으로 0~100점으로 변환한다.

예:

```text
거리 적합도      95
경사도           82
화장실           90
편의점           75
공원             70
야간 인프라      92
```

---

## 16. 사용자 가중치 적용

사용자는 각 조건의 중요도를 1~5 단계로 설정한다.

예:

```text
거리       5
경사도     4
화장실     5
편의점     2
공원       3
야간       5
```

최종 점수는 다음 방식으로 계산한다.

```text
Final Score

=

각 Feature 점수 × 사용자 중요도

÷

전체 중요도 합
```

예:

```text
거리        95 × 5
경사        85 × 4
화장실      90 × 5
편의점      70 × 2
공원        75 × 3
야간        92 × 5

↓

최종 조건 충족도
89.7점
```

## 17. 최종 추천

후보 경로별 최종 점수를 계산한 후 점수가 높은 순서대로 정렬한다.

단, 비슷한 경로가 TOP 3를 차지하지 않도록 유사 경로를 제거한다.

최종적으로:

```text
1위 코스
조건 충족도 91%

2위 코스
조건 충족도 87%

3위 코스
조건 충족도 83%
```

형태로 제공한다.

조건을 만족하지 못한 경우 해당 이유도 같이 제공한다.

예:

```text
✓ 목표 거리 만족
✓ 화장실 조건 만족
✓ 야간 인프라 높음
△ 편의점 조건 일부 미충족
```
