# 후보 경로 생성 - 현재 한계점

> [!info] 빠른 위치 파악
> - **상태:** 현재 구현
> - **소스 위치:** `routing-worker/src/algo/routing/*, scoring/edge_cost.py`
> - **역할:** 현재 구현의 알려진 제약과 이미 인지한 개선 대상을 한곳에 기록한다.
> - **이전 단계:** [[14. Candidate Pool 필터링]]
> - **다음 단계:** [[../02. 특징 추출/INDEX|02. 특징 추출]]
> - **주요 입력:** 현재 구현 분석
> - **주요 출력:** 수정/검토 체크리스트

> [!important]
> 아래 항목은 **현재 팀에서 이미 인지하고 있는 한계**다. 문서에는 문제를 숨기지 않고, 현재 구현과 변경 예정 상태를 구분하기 위해 기록한다.

| ID | 현재 한계 | 상태 | 예정 방향 |
|---|---|---|---|
| ROUTE-01 | Via 사용 시 LOOP와 ROUND_TRIP의 생성 의미가 사실상 동일 | 인지 완료 | 모드별 Via 의미 분리 검토 |
| ROUTE-02 | `scale *= target/actual`의 수렴 보장 없음 | 인지 완료 | 반복별 damping 검토 |
| ROUTE-03 | ONE_WAY 타원의 bearing과 parameter angle 직접 매핑 | 인지 완료 | 측면 waypoint/허용 영역 원리 재검토 |
| ROUTE-04 | 기본 12 bearing을 8 ellipse point에 매핑하여 중복 선택 가능 | 인지 완료 | 타원 후보 생성 규칙과 함께 검토 |
| ROUTE-05 | MultiDiGraph에서 선택된 edge key를 NodePath에 보존하지 않음 | 인지 완료 | `(u,v,key)` 식 edge path 또는 일관된 edge 선택 검토 |
| ROUTE-06 | `FEATURE_COST_SCALES`, slope 기준 등이 heuristic 고정값 | 인지 완료 | 실제 데이터 분포/평가 결과로 tuning |
| ROUTE-07 | Via 거리 하드컷 10%가 일부 config와 분리되어 직접 기록됨 | 인지 완료 | 공통 config 사용 검토 |
| ROUTE-08 | 후보 다양성은 제한된 bearing/waypoint 휴리스틱에 의존 | 인지 완료 | 프로젝트 범위 내 우선 현재 방식 유지 |

## 현재 수준 표현

> 사용자 선호를 탐색 비용에 반영한 **휴리스틱 기반 개인화 경로 생성 알고리즘**이며, 프로젝트 MVP 수준의 후보 다양성과 개인화를 목표로 한다.

단순 `length` 최단경로보다 발전된 구조이지만, 실서비스 routing engine 수준의 최적성/안전성/접근성 검증까지 완료된 상태로 표현하지 않는다.
