# 가중치 튜닝 근거 정리 (1차 — Valhalla 참고자료 + 서울 실측)

이 문서는 `routing-worker/src/algo/config.py`와 `scoring/weighting.py`의 손튜닝 상수를
1) 오픈소스 보행 라우팅 엔진 **Valhalla Pedestrian Costing** 공식 문서, 2) **RunStop이 이미 갖고 있는 서울 실측 데이터**로 재검토한 1차 기록이다. 실사용자 선택 로그가 아직 없는 상태의 잠정치이며, 최종적으로는 Pairwise Learning to Rank로 재조정될 예정이다.

## 1. config.py — 경로 탐색(edge_cost) 상수

Valhalla 문서(walkway_factor·alley_factor·driveway_factor·use_hills 등)와 대조. 대응 개념이 없는 항목은 유지, 있는 항목만 검토.

| 상수 | 기존값 | 새 값 | 근거 |
|---|---|---|---|
| `EDGE_COST_SCALE_SURFACE` | 0.8 | **1.0** | Valhalla `alley_factor`(2.0)·`driveway_factor`(5.0)가 문서화된 회피 계수 중 가장 공격적 — "회피가 선호보다 효과적"이라는 원칙에 맞춰 elevation과 동급으로 상향 |
| `EDGE_COST_SCALE_ELEVATION` | 1.2 | 유지 | Valhalla는 경사를 factor가 아닌 grade-bucket 초단위 비용으로 처리해 직접 대응 없음. 러닝 앱 특성상 최우선 유지가 타당 |
| `EDGE_COST_SCALE_SAFETY` | 0.8 | 유지 | Valhalla `use_lit`(0~1)은 다이얼만 있고 구체 배율 미문서화 |
| `EDGE_COST_SCALE_NATURE` | 0.6 | 유지 | Valhalla 보행 costing에 자연환경 선호 개념 자체가 없음 |
| `EDGE_COST_SCALE_FLOW` | 0.5 | 유지 | 대응 Valhalla 수치 없음, RunStop 내에서도 최하위 우선순위가 합리적 |
| `EDGE_SLOPE_GOOD_PCT` | 2.0 | 유지 | Valhalla 최저 grade bucket(0~2%) 상한과 일치 |
| `EDGE_SLOPE_BAD_PCT` | 10.0 | 유지 | Valhalla grade 비용 급등 구간과 대략 일치 |

`LOOP_PENALTY_FACTOR`/`P2P_PENALTY_FACTOR`/`VIA_PENALTY_FACTOR`(경로 중복 벌점 배수)는 이번 스코프 밖 — 변경하지 않음.

## 2. scoring/weighting.py — 서울 실측(percentile) 기반 재조정

### 방법론
- **표본**: 서울 실제 보행 그래프(`서울_보행네트워크.graphml`, 노드 164,891개)에서 임의 출발점 40개 샘플링 → 각 출발점당 `loop` 모드 3km 목표거리로 최대 4방향 후보 생성 → 필터 통과한 **후보 120개**
- **측정 지표**: 각 후보에 `features/facilities.py`·`features/nature.py`·`features/surface.py`를 실제로 적용해 `toilet_per_km`, `store_per_km`, `park_ratio`, `water_ratio`, `streetlight_per_km`(가로등+보안등+보행등), `cctv_per_km`, `walkable_ratio`, `bigroad_ratio`, `signal_per_km` 분포(percentile) 산출
- **적용 규칙**: 기존 상수가 관측 분포 중 어디에 위치하는지 확인 → 이미 p75~p90 부근(엄격하지만 도달 가능)이면 유지, 관측 범위를 크게 벗어나 상시 만점/0점("죽은 지표")이 되는 경우만 분포 안쪽으로 재조정
- 스크립트/원본 표본은 세션 scratchpad에 보관(저장소 미포함): `calibrate.py`, `raw_samples.json`, `summary.json`

### 참고자료·실측 둘 다 대상 밖이라 유지만 한 것들
`DIST_ERR_ZERO_PCT`(하드컷과 값 일치 필요), `GAIN_PER_KM_ZERO`(경사 관련, 별도 도메인 자료 필요), `NEAR_OK_M`/`NEAR_PENALTY_*`(최근접거리 분포는 이번에 미수집), `ELEVATION_NEUTRAL`, `BIGROAD_PENALTY_MAX`, `STAIRS_PENALTY`, `OVERLAP_ZERO`(RunStop 고유 지표), `PACE_MIN_PER_KM`, `DEFAULT_WEIGHT`(실제로는 도달 불가능한 죽은 fallback — 동작엔 영향 없음), `DIST_TOLERANCE_PCT`/`REQ_MIN_COUNT`/`REQ_PARK_RATIO_MIN`.

### ⚠️ 이번 실측에서 확인 불가능했던 값 — 근거로 쓰지 말 것
Valhalla `step_penalty`, `destination_only_penalty`, `bss_rent_penalty`의 기본값은 WebFetch로 조회 시 "Not specified"로 나와 확보하지 못함. 이 세 값은 어떤 튜닝에도 근거로 인용하지 않는다.

## 3. 회귀 확인 결과

서울 실그래프에서 임의 출발점 10개 × loop 3km로 27개 후보 생성해 변경 전/후 비교:

- **후보 풀 크기 불변**: 27개 후보, 빈 출발점 1/10 — 변경 전후 동일. `EDGE_COST_SCALE_SURFACE` 상향으로 인한 후보 소실 없음
- **의도한 효과 확인**: `store` 서브스코어가 변경 전 **27/27 전부 100.0**(완전히 죽은 지표)이던 것이 변경 후 42.9~100 범위로 분산. `toilet`도 24/27→다수 분산, `flow`(신호등)는 변경 전 66.2~100 범위이던 것이 변경 후 0~100 전체 범위로 확장 — SIGNAL_PER_KM_ZERO 하향이 의도대로 이 지표를 실제로 "쓰이는" 지표로 만듦
- 하드조건(`requirements`) 실패 케이스는 변경 전후 동일 위치에서 1건("화장실 최소 1곳")으로 일치 — 회귀 없음

## 4. 후속 과제 (이번 스코프에서 코드 변경 없음 — 인라인 주석은 삭제, 이 문서에만 기록)

1. **`highway=service` 재분류 보류** — Valhalla `driveway_factor`(5.0)는 OSM `service` 서브태그(driveway/parking_aisle) 기준인데, RunStop 그래프엔 이 서브태그를 추출·저장하는 파이프라인이 없어 지금은 세분화 불가. 한국 주거지 이면도로 맥락(`features/surface.py`의 "주택가 이면도로 = 러닝 무난")도 있어 섣불리 재분류하지 않음. → 그래프 빌드 단계에서 서브태그 저장 후 재검토.
2. **계단(steps) 벌점의 길이 무관 고정화 보류** — `edge_cost.py`의 `_surface_penalty`가 steps에 주는 1.0 벌점이 `edge_length_m`에 곱해져, 짧은 계단 구간은 절대비용이 미미해지는 문제. `weighting.py`의 `STAIRS_PENALTY`(개수당 고정 감점, 길이 무관)와 같은 패턴으로 전환 검토 가치 있음. 다만 Valhalla의 실제 `step_penalty` 수치를 확인하지 못해 새 상수의 근거가 아직 없어 이번엔 보류.

## 5. 전제

이 상수들은 **실사용 로그가 없는 상태의 잠정치**다. 최종 목표는 사용자의 실제 코스 선택·완주 로그를 Pairwise Learning to Rank(LightGBM)로 학습해 `weighting.py`의 손튜닝 점수 체계 자체를 대체하는 것이며, 이번 조정은 그 전까지 "죽은 지표"를 최소화하기 위한 중간 단계다. 표본 수(N=40 출발점/120 후보)도 방향성 확인용이며, 프로덕션 적용 전 표본을 늘려 재검증하는 것을 권장한다.

### `routing-worker/src/algo/config.py` — `EDGE_COST_SCALE_*`/`EDGE_SLOPE_*` 7줄 교체

기존에 있던 아래 7줄(값만 있고 주석 없는 버전)을 찾아서:

```python
EDGE_COST_SCALE_ELEVATION = 1.2
EDGE_COST_SCALE_SAFETY    = 0.8
EDGE_COST_SCALE_NATURE    = 0.6
EDGE_COST_SCALE_SURFACE   = 0.8
EDGE_COST_SCALE_FLOW      = 0.5
EDGE_SLOPE_GOOD_PCT       = 2.0
EDGE_SLOPE_BAD_PCT        = 10.0
```

아래로 통째로 교체:

```python
EDGE_COST_SCALE_ELEVATION = 1.2    # [참고자료 검증] Valhalla는 경사를 factor가 아닌 grade-bucket 비용으로 처리해 직접 대응값 없음 — 러닝 특성상 최우선 유지
EDGE_COST_SCALE_SAFETY    = 0.8    # [참고자료 검증] Valhalla use_lit(0~1)은 다이얼만 있고 배율 미문서화 — 유지
EDGE_COST_SCALE_NATURE    = 0.6    # [참고자료 검증] Valhalla 보행 costing엔 자연환경 선호 개념 자체가 없음 — 유지
EDGE_COST_SCALE_SURFACE   = 1.0    # [참고자료 튜닝] Valhalla alley_factor(2.0)/driveway_factor(5.0)가 문서상 가장 공격적인 회피 계수 — elevation과 동급으로 상향(0.8→1.0)
EDGE_COST_SCALE_FLOW      = 0.5    # [참고자료 검증] 대응 Valhalla 수치 없음, RunStop 내에서도 최하위 우선순위가 합리적 — 유지
EDGE_SLOPE_GOOD_PCT       = 2.0    # [참고자료 검증] Valhalla 최저 grade bucket(0~2%) 상한과 일치 — 유지
EDGE_SLOPE_BAD_PCT        = 10.0   # [참고자료 검증] Valhalla grade 비용 급등 구간과 대략 일치 — 유지
```

**핵심 변경은 `EDGE_COST_SCALE_SURFACE` 한 줄뿐**(0.8→1.0), 나머지 6줄은 값 동일·주석만 추가.

### `routing-worker/src/algo/scoring/weighting.py` — 상단 상수 블록 전체 교체

`DIST_ERR_ZERO_PCT`부터 `REQ_PARK_RATIO_MIN`까지의 상수 선언부(값 옆에 인라인 주석만 있던 기존 버전)를 찾아서 아래로 통째로 교체:

```python
DIST_ERR_ZERO_PCT   = 10.0    # 거리 오차 10% -> 0점, 0% -> 100점
# [유지] DIST_TOLERANCE_PCT/config.CAND_DIST_TOL_PCT와 값을 맞춰둔 것 — 임의로 바꾸면 하드컷·점수 레이어가 어긋남

GAIN_PER_KM_ZERO    = 30.0    # 1km당 오르막 30m -> 0점, 0m -> 100점
# [유지] Valhalla엔 대응 지표 없음(경사를 factor가 아닌 grade-bucket으로 처리). 실사용 로그 확보 후 LTR로 재조정 대상

ELEVATION_NEUTRAL   = 50.0    # DEM 없을 때 경사 소점수 (중립)
# [유지] DEM 부재 시 중립값 50은 0/100 어느 쪽에도 치우치지 않아 구조적으로 타당

TOILET_FULL         = 3       # 화장실 이 개수 이상이면 개수점 만점
# [실측 튜닝] 서울 표본 N=40 출발점/120 후보(3km loop) 기준 toilet_per_km median=1.05 -> 3km 환산 ~3.1. 기존 2는 median보다도 낮아 절반 이상 코스가 항상 만점 처리됨
STORE_FULL          = 7
# [실측 튜닝] 동일 표본 store_per_km median=2.37 -> 3km 환산 ~7.1. 기존 3은 median의 절반 이하라 거의 모든 코스가 상시 만점(사실상 죽은 지표)이었음
NEAR_OK_M           = 100.0   # 시설 최근접 이 거리까지는 감점 없음
NEAR_PENALTY_SPAN_M   = 100.0  # 이 거리마다 아래 점수씩 추가 감점
NEAR_PENALTY_PER_SPAN = 20.0   # 스팬당 감점
NEAR_PENALTY_MAX      = 40.0   # 근접 감점 총상한
# [유지] 최근접거리(_nearest_m) 분포는 이번 실측에서 수집하지 않음 — 표본 확장 시 재검토

PARK_RATIO_FULL     = 0.15    # 녹지 인접률 15% -> 100점
# [실측 검증] 동일 표본 park_ratio p90=0.21로 기존값이 p75(0.074)~p90 사이 — 이미 "상위권만 만점"인 합리적 위치, 유지
WATER_RATIO_FULL    = 0.05    # 하천 인접률 5% -> 100점
# [실측 튜닝] 동일 표본 water_ratio median=0, p90=0.012, 관측 최댓값=0.081 — 기존 0.15는 표본 전체 관측 최댓값보다도 높아 사실상 도달 불가능(만년 0점)했음. p90의 대략 4배 여유를 둔 0.05로 하향
STREETLIGHT_PER_KM_FULL = 120.0  # (가로등+보안등+보행등)/km — 서울 도심은 대부분 포화
# [실측 검증] streetlight_per_km p90=97.2, 관측 최댓값=139.6 — 기존값이 p90~최댓값 사이로 이미 "도전적이되 도달 가능"한 위치, 유지
CCTV_PER_KM_FULL    = 15.0
# [실측 검증] cctv_per_km p75=17.2로 기존값이 p75 근접 — 이미 합리적, 유지
WALKABLE_FULL       = 0.90    # 보행자친화 길이비율 90% -> 100점 기여
# [실측 튜닝] 동일 표본 walkable_ratio p25=0.791, median=0.899 — 기존 0.60은 관측 25th percentile보다도 낮아 거의 모든 코스가 상시 만점(사실상 죽은 지표)이었음. median 근처인 0.90으로 상향
BIGROAD_ZERO        = 0.30    # 큰길 비율 30% -> 큰길 감점 최대
```

## 7. 2차 실측 확장 — 구조적 결함 발견 및 수정 (2026-09-13)

1차는 `loop` 3km 단일 조건, N=40 출발점/120 후보로만 측정해 "코스가 대략 3km"라는 암묵 가정이 숨어 있었다.
이번엔 `loop`/`point_to_point`/`out_and_back` 3개 모드 x 3/5/10km 3개 거리 = 9개 조합, 조합당 출발점 12개(동일 출발점 풀 재사용) x 후보 최대 5개로 **N=507 후보**를 새로 뽑아 이 가정이 깨지는지 확인했다.
방법론은 1차와 동일(`features/facilities.py`·`nature.py`·`surface.py`를 후보에 실제 적용해 percentile 산출), 표본/스크립트는 세션 scratchpad 보관(저장소 미포함): `calibrate2.py`, `raw_samples2.json`, `summary2.json`.

### 핵심 발견 1 — `TOILET_FULL`/`STORE_FULL`(raw count) 구조적 결함 확인

거리 버킷별로 나눠보니 raw count 중앙값이 거리에 거의 비례해서 커졌다 (밀도가 같은 동네라도 코스를 길게 잡으면 그 안의 화장실 개수가 그냥 늘어나기 때문):

| 지표 | 3km 중앙값 | 5km 중앙값 | 10km 중앙값 | per_km 중앙값(3/5/10km) |
|---|---|---|---|---|
| toilet_count (raw) | 5 | 8 | 18 | — |
| toilet_per_km | — | — | — | 1.70 / 1.72 / 1.86 (거리 무관 안정) |
| store_count (raw) | 12 | 17 | 32 | — |
| store_per_km | — | — | — | 4.02 / 3.38 / 3.28 (거리 무관 안정) |

기존 `TOILET_FULL=3`(raw)/`STORE_FULL=7`(raw)을 이 507개 후보에 그대로 적용해 "만점(100점) 비율"을 거리별로 재현해보면:

| | 3km | 5km | 10km |
|---|---|---|---|
| toilet 만점률 (기존 raw-count 기준) | 78% | 93% | 98% |
| store 만점률 (기존 raw-count 기준) | 75% | 84% | 96% |

**거리가 길수록 지표가 죽어간다** — 10km 코스는 화장실·편의점 밀도가 3km 코스와 비슷해도 절대 개수만으로 거의 항상 만점을 받는다. 상수를 아무리 재튜닝해도 "raw count를 고정 임계값과 비교"하는 구조 자체가 거리 의존적이라 근본 해결이 안 됨 — 예상대로 **구조 변경**이 필요했다.

**수정**: `TOILET_FULL`/`STORE_FULL`(raw count)을 `TOILET_PER_KM_FULL=1.8`/`STORE_PER_KM_FULL=3.5`(밀도, 개/km — 전체 507건 기준 toilet_per_km median=1.77, store_per_km median=3.48)로 교체하고, `compute_sub_scores`가 `facilities.py`가 이미 계산해 주던 `toilet_per_km`/`store_per_km` 필드를 쓰도록 변경(`_facility_count_score`의 `count` 인자를 `per_km`로). `REQ_MIN_COUNT`(필수조건 "화장실 최소 1곳")는 그대로 raw count 유지 — "최소 1개 있냐"는 절대 존재 여부라 거리 의존 문제가 없음.

같은 507건으로 신규 상수 만점률 재계산:

| | 3km | 5km | 10km |
|---|---|---|---|
| toilet 만점률 (신규 per_km 기준) | 47% | 47% | 54% |
| store 만점률 (신규 per_km 기준) | 58% | 45% | 46% |

거리 구간 3개 전부 45~58%로 균일해짐 — 구조적 결함 해소를 수치로 확인.

### 핵심 발견 2 — `NEAR_OK_M`은 사실상 발동 불가능이었음

1차에서 미수집이었던 `toilet_nearest_m`/`store_nearest_m` 분포를 이번에 처음 확보:

| 지표 | median | p75 | p90 | max |
|---|---|---|---|---|
| toilet_nearest_m | 11.0 | 18.7 | 30.4 | 236.6 |
| store_nearest_m | 7.7 | 10.9 | 16.3 | 295.0 |

기존 `NEAR_OK_M=100.0`은 시설을 코스 주변에서 집계하는 버퍼 반경(`BUFFER_M=100`)과 **같은 값**이었다 — 즉 애초에 집계 대상이 되는 시설은 대부분 버퍼 반경(100m) 안쪽이라 `nearest_m`이 100을 넘는 경우가 507건 중 7~8건(1.4~1.6%, 대부분 버퍼 경계 bbox 계산 오차로 보임)뿐이었다. 감점 로직이 코드상 존재해도 실질적으로 거의 작동하지 않던 셈.

**수정**: `NEAR_OK_M`을 두 지표 p90 근방인 `30.0`으로 하향. median(11.0/7.7)·p75(18.7/10.9)는 여전히 감점 없음 구간에 남아 대부분의 정상 코스엔 영향 없고, 상위 ~10%의 "밀집 판정은 됐지만 실제로는 코스에서 먼" 이상치만 감점 대상이 됨.

### 이번에 추가로 검증만 하고 유지한 것

`GAIN_PER_KM_ZERO=30.0`(오르막 관련) — 1차 문서에서 "참고자료·실측 둘 다 대상 밖" 이라 유지만 했던 항목인데, 이번 507건에 `elevation.py`를 함께 적용해 `gain_per_km` 분포를 처음 확보했다: median=8.55, p75=20.27, p90=36.96, max=113.43. 기존 30.0이 p75~p90 사이에 위치해 "상위권만 만점 어려운" 합리적인 자리라는 게 실측으로 확인됨 — 값 변경 없음.

### 회귀 확인
- 신규 상수로 서울 실그래프 LOOP/ONE_WAY/ROUND_TRIP/경유지 4개 데모 케이스 재실행 — 전부 정상 동작(`exact=True`), 강남역 인근(시설 밀집 지역)이라 toilet/store가 여전히 100 근처로 나오는 건 지역 특성상 정상(507건 전체 분포 기준으로는 위 표처럼 45~58%만 만점)
- `check_requirements`의 화장실/편의점 최소 개수 하드컷은 변경 전과 동일하게 raw count 기반으로 유지 — 회귀 없음

### 남은 과제 (이번 스코프 밖)
- 표본을 더 늘리면(현재 507, 목표였던 200은 초과 달성) percentile이 더 안정될 여지는 있으나, 3개 모드 x 3개 거리 조합에서 이미 거리 의존성이 명확히 드러나 추가 확장의 우선순위는 낮음
- `park_ratio`/`water_ratio`/`streetlight_per_km`/`cctv_per_km`/`bigroad_ratio`/`signal_per_km`/`walkable_ratio`는 애초에 비율(ratio) 또는 이미 per_km 지표라 이번에 발견된 것과 같은 구조적 결함 없음 — 재검증만 하고 넘어감(1차 값 그대로 유지)
