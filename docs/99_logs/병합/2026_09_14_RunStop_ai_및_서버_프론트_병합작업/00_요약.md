## 최종 방향

이번 병합은 한쪽 변경을 통째로 선택하지 않고 다음 기준으로 조합했다.

```text
Frontend 새 요청/응답 계약
  + Node API/DTO/DB 저장 흐름
  + Python routing-worker maxSlope/facilityPreferences 전달
  + 기존 personal/hurwan 알고리즘, scoring, AI 학습 규격
```

## 핵심 결정

### `facilityPreferences`

프론트/서비스 요청 계약에서는 다음 형태를 유지한다.

```json
{
  "facilityPreferences": {
    "toilet": "PREFER",
    "store": "IGNORE"
  }
}
```

AI 학습 규격에서는 이 값이 `requirements.toilet = true`와 비슷한 의미로 맞춰져 있으므로, 실제 AI 호출 경계에서는 변환할 수 있게 했다.

현재 fallback 정렬에서는 AI를 호출하지 않으므로 변환 함수를 실행하지 않는다.

### `maxSlope`

프론트/Node 계약에서는 `maxSlope`를 유지하고, Python parser에서 알고리즘 내부 규격인 `requirements["max_slope_pct"]`로 변환한다.

```text
Frontend/Node: elementConditions.maxSlope
Python parser: requirements["max_slope_pct"]
Routing/scoring: max_slope_pct 조건 사용
```

### 후보 정렬

최종 selector fallback은 `_candidate_sort_key()`가 아니라 기존 `condition_score` 내림차순 정렬을 유지한다.

시설 선호는 이미 `score_candidate()`의 `condition_score` 계산에 반영되므로 selector에서 한 번 더 강제 정렬하지 않는다.
