# (임시) RunStop 멘토링 질문

## 현재 고려 중인 구조

학습 단계에서는
1. 알고리즘 결과를 학습하는 경로 생성 AI
2. 생성된 후보 중 적합한 경로를 선택하는 경로 추천 AI

두 모델을 분리하여 학습하고,
서비스에서는 두 과정을 하나의 파이프라인으로 연결할 예정입니다.


## 질문

1. Dijkstra 등의 알고리즘으로 생성한 경로를 학습시켜,
   AI가 더 적은 연산으로 유사한 경로를 생성하도록 하는 방식이 타당할까요?
   알고리즘으로 명확히 해결 가능한 문제를 AI로 근사할 때 특히 고려할 점이 궁금합니다.

2. 경로 생성 AI와 경로 추천 AI를 모두 구현하면 프로젝트 범위가 너무 커질까요?
   하나를 줄인다면 어느 부분을 알고리즘으로 유지하는 것이 적절할까요?

3. 여러 경로 후보를 팀에서 평가하여 추천 모델의 학습 데이터를 만들려고 합니다.
   이때 평가 기준, 라벨 방식, 데이터 수 등에서 주의할 점이 있을까요?

4. 경사도, 가로등, CCTV, 화장실, 편의점, 보행자도로 등의 공간 데이터를
   경로 단위 Feature로 가공해 모델에 사용하는 방식은 적절할까요?

5. 경로 알고리즘, AI 모델, 공간 데이터, TMAP 등의 외부 API를
   하나의 서비스로 연결할 때 예상되는 주요 충돌 지점이나 병목은 무엇일까요?

6. 현재 `프론트엔드`는 피그마와 AI를 활용한 빠른 구현 / `백엔드` / `AI 모델링` / `데이터 파이프라인 구성` 등으로 분업을 고려하고 있습니다.
   프로젝트 규모에서 더 효율적인 분업 방식이 있을까요?

7. 현재 기획에서 구현 비용에 비해 가치가 낮거나,
   프로젝트 완성도를 위해 과감히 제외하는 것이 좋을 부분이 있다면 무엇일까요?

8. 기능 구현을 넘어 실제 서비스처럼 완성도를 높이기 위해
   현업에서 특히 신경 쓰는 부분이나 요령이 있다면 궁금합니다.

# 답변

1. 알고리즘 결과 학습 기각
2. 추천 알고리즘이 더 좋음
3. 라벨링 전에 평가 기준 문서화
4. 공간 데이터 경로 단위 Feature은 단위 통일 필수, 매번 검색은 비추
5. 서비스간 인터페이스 모두 정리하여 단위 및 DTO를 정확하게 맞춰두기
6. 데이터 파이프라인을 가장 먼저 끝내야함. 더미응답 API 형태로 만들어서 백엔드랑 붙여가는 방향
7. 알고리즘을 AI로 바꾸는거 제거
8. 안되는 경우, 서비스가 멈추는 경우 등에 대해서 처리 화면 또는 서버 예외처리 확실하게 하기

```
(주)인포와이즈_이영현책임  [오후 9:23]
1. 알고리즘 결과 학습
 솔직히 말하면 이건 비추천이에요. Dijkstra는 정답을 보장하는데 그걸 흉내내는 AI는 정답 보장도 안 되면서 학습 비용만 드는 셈이거든요. 알고리즘 개선으로 푸는 걸 추천드립니다.
2. 두 모델 다 하면 범위가 너무 큰가
 네, 확실히 큽니다. 저같으면 경로 생성은 알고리즘으로 두고 추천만 AI로 갈거 같아요. 추천 쪽이 "정답이 없는 문제"라 AI를 쓸 명분도 확실하고, 포트폴리오에서 설명하기도 훨씬 좋아요.
3. 팀이 직접 라벨링할 때 주의할 점
 사람마다 좋은 경로 기준이 달라서 라벨이 흔들리는 게 제일 큰 함정이에요. 라벨링 전에 평가 기준표부터 문서로 합의하고, 점수 매기기보다는 둘 중 어느 경로가 나은가 비교 방식이 훨씬 일관성 있게 나옵니다.
4. 공간 데이터를 경로 단위 Feature로 가공
 이건 저도 직접 해본 영역은 아니라서 정답이라고 말씀드리긴 어렵습니다. 다만 데이터마다 좌표계가 다를 수 있으니 통일 작업이 먼저고, 경로마다 주변 시설을 매번 검색하면 느려질 테니 성능 쪽은 미리 고민해보시면 좋을 것 같습니다.
5. 경로 알고리즘·AI 모델·공간 데이터·외부 API를 하나로 연결할 때 충돌 지점과 병목
 충돌은 대부분 데이터 형식에서 나요. 알고리즘이 만든 경로, AI 모델 입력, 공간 데이터, TMAP이 요구하는 좌표가 전부 형식이 달라서 중간 변환에서 어긋나기 쉬우니, 컴포넌트 간 주고받을 형식을 처음에 딱 정해두는 게 중요합니다.
6. 분업 방식
 나누신 방향은 괜찮은데 데이터 파이프라인을 제일 먼저 끝내야 AI 파트가 놀지 않아요. 그리고 AI 담당이 모델만 붙잡고 있으면 통합할 때 고생하니까, 처음부터 더미 응답이라도 주는 API 형태로 만들어서 백엔드랑 계속 붙여보면서 가는 걸 추천합니다.
7. 뺄 것
 2번에서 말씀드린 대로 경로 생성 AI를 빼는 게 제일 효과가 클것으로 보입니다.
8. 실서비스 느낌 내는 요령
 현업에서 제일 신경 쓰는 건 잘 될 때가 아니라 안 될 때예요. 조건에 맞는 경로가 없을 때, 로딩이 길어질 때, API가 죽었을 때 등등 화면이 어떻게 보이는지, 또는 어떻게 처리하는지가 완성도를 결정합니다.

그리고 추가적으로 궁금한게 이번 프로젝트에서 사용자가 조건을 자연어로 입력한다고 하는데 어떠한 질의를 예상하는지 궁금합니다. 문서상에선 적당히 짧은코스, 오르막이 별로 없는 길 이런 질문을 예시로 든거 같은데 이를 벗어난 질문을 할시 어떻게 처리하려는지 궁금합니다. (편집됨)
```
