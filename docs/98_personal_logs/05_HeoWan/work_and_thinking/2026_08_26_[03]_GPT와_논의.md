초기 DBML을 작성하는 과정에서 FK 컬럼의 nullable 상태와 DBML 관계 표현 때문에 경고가 발생하였다.

## 3. OAuth 및 사용자 구조 논의

초기에는 Google OAuth와 Kakao OAuth를 모두 고려하고 있었다.

Google OAuth의 흐름에 대해서는 다음과 같이 인식하고 있었다.

1. Google 로그인 / 동의 화면 URL 요청
2. 인증 결과를 이용한 Token 발급 요청
3. 사용자 ID를 기반으로 사용자 정보 확인

Google OpenID Connect에서는 `openid`를 사용하고, `sub`를 Google 사용자를 식별하는 값으로 사용할 수 있다는 점을 확인하였다.

Refresh Token도 존재하지만 현재 DB 설계와 서비스 범위를 정하는 단계에서는 우선 중요도를 낮게 두었다.

Google과 Kakao를 동시에 지원할 경우 같은 실제 사용자가 각각 다른 Provider로 로그인했을 때 두 계정이 동일한 사람이라는 공통 식별자가 자동으로 존재하지 않는다는 문제도 논의하였다.

이를 해결하기 위해 처음에는 마이페이지에서 다른 OAuth 계정을 직접 연동하는 방식을 고려하였다.

구조는 다음과 같았다.

* users 1 : N user_auths

하나의 RunStop 사용자에 여러 OAuth 인증 정보를 붙일 수 있게 만드는 방식이다.

하지만 개발 기간이 약 한 달이고, 계정 연결과 회원가입 상태 관리까지 구현하면 기술 비용이 커질 수 있다고 판단하였다.

최종적으로 현재 프로젝트에서는 다음과 같이 결정하였다.

* Google OAuth 단일 로그인 방식 사용
* 별도의 회원가입 Form 구현하지 않음
* RunStop에서 추가로 사용자 정보를 입력받는 가입 단계도 두지 않음
* 최초 Google 로그인 성공 시 users 생성
* user_auths에는 Google 인증 정보 저장
* provider_user_id에는 Google의 `sub` 저장
* 현재 provider는 GOOGLE만 사용

다만 `users`와 `user_auths` 테이블을 분리하는 구조는 그대로 유지한다.

향후 Kakao 등 다른 Provider를 추가하게 될 경우 계정 병합 및 경험치, 러닝 기록 등의 병합 정책을 별도로 설계할 수 있다는 확장 가능성은 발표에서 설명할 수 있도록 하기로 하였다.

사용자가 직접 입력하는 별도의 프로필 정보 역시 현재는 받지 않기로 하였다.

기존 `user_profile`에 고려하던 체력 수준, 선호 경사, 선호 시설, 선호 환경 등은 실제 알고리즘에서 어떤 값을 사용할지 아직 결정되지 않았기 때문에 지금 컬럼을 확정하지 않기로 하였다.

현재 단계에서는 `user_profile` 자체를 제외하고, 향후 알고리즘 Feature가 확정되면 필요한 사용자 데이터만 다시 추가하는 방향으로 정리하였다.

## 4. users 기본 상태와 경험치

사용자가 Google 로그인을 통해 최초 생성되면 기본 상태를 갖도록 한다.

* `total_exp = 0`
* `role = USER`

role은 다음 두 종류로 정의한다.

* USER
* ADMIN

일반 사용자가 로그인 또는 가입 과정에서 ADMIN을 선택할 수 있게 하지 않고, 관리자 권한은 서비스 내부에서 별도로 부여하는 구조로 생각하였다.

경험치는 기본적으로 실제 러닝 기록을 기준으로 계산하는 방향을 논의하였다.

목표 달성 시 추가 경험치를 제공하는 방식도 고려하였다.

레벨이 높아질수록 동일한 목표가 지나치게 쉬워지는 문제를 막기 위해 다음과 같은 후보 정책을 이야기하였다.

* 레벨에 따라 목표 달성 보상이 조금씩 감소
* 레벨에 따라 보상을 받기 위한 최소 목표 거리 증가
* 최소 거리 증가에는 적절한 상한 또는 매우 작은 증가폭 사용

정확한 경험치 공식과 임계치는 이후 결정하기로 하였다.

## 5. running_goal 정책

`running_goal`은 다음 두 종류의 목표를 가진다.

* WEEKLY
* MONTHLY

처음에는 진행 중인 목표의 값을 수정할 수 있도록 할지 논의하였다.

하지만 기존 목표를 직접 수정하면 과거에 어떤 목표를 가지고 있었는지 기록이 사라질 수 있기 때문에 목표 자체를 UPDATE하는 방식 대신 기존 목표를 종료하고 새 목표를 만드는 방향으로 정리하였다.

목표 상태는 다음 네 가지로 정의하였다.

* ACTIVE
* SUCCESS
* FAILED
* STOPPED

각 의미는 다음과 같다.

* ACTIVE: 진행 중
* SUCCESS: 목표 달성
* FAILED: 기간이 끝났지만 목표 미달성
* STOPPED: 사용자가 직접 중단

시간 관련 컬럼은 다음과 같이 구분하였다.

* `start_date`: 목표 시작일
* `end_date`: 예정된 목표 종료일
* `finished_at`: 목표가 실제 종료된 시간

별도의 `stopped_at`은 만들지 않기로 하였다.

`status = STOPPED`와 `finished_at`을 같이 보면 사용자가 언제 목표를 중단했는지 알 수 있기 때문이다.

SUCCESS나 FAILED인 경우에도 동일하게 `finished_at`을 사용할 수 있다.

사용자가 진행 중인 목표를 바꾸고 싶을 경우에는 다음 흐름을 사용한다.

1. 기존 목표를 STOPPED 처리
2. `finished_at` 저장
3. 새로운 running_goal 생성

따라서 목표를 중단하더라도 이전까지의 기록은 유지되고, 바로 새로운 목표를 설정할 수 있다.

## 6. GPS 기록과 running_session

`running_trackpoint`는 러닝 중 N초에 한 번씩 찍는 GPS Snapshot으로 정의하였다.

기본적으로 다음 정보를 가진다.

* latitude
* longitude
* recorded_at
* accuracy

`accuracy`는 우리가 기지국 개수나 별도 알고리즘을 이용해 계산하는 값이 아니다.

모바일 OS 또는 GPS / 위치 API가 제공하는 위치 정확도 추정값을 그대로 받아 저장하는 것으로 이해하였다.

따라서 accuracy 자체를 계산하기 위한 별도의 로직은 필요하지 않고, 추후 GPS 이상치를 판단하는 보조값으로 활용할 수 있다.

`running_session`은 사용자가 러닝을 시작하고 종료할 때까지의 한 번의 러닝 전체를 의미한다.

예를 들어 한 번의 40분 러닝이 하나의 running_session이고, 그 40분 동안 수집된 수백 개의 GPS 지점이 running_trackpoint가 된다.

관계는 다음과 같다.

* running_session 1 : N running_trackpoint

또한 running_session에는 해당 러닝을 수행한 사용자를 직접 연결하기 위해 `user_idx` FK를 두기로 하였다.

이는 기록을 조회할 때 경로 관련 테이블을 여러 단계 JOIN하여 사용자를 찾는 것을 피하고, 세션 자체가 누구의 러닝인지 명확하게 나타내기 위함이다.

users는 soft delete만 고려하고 있으며 users.idx는 변경되지 않는 식별자로 사용할 예정이다.

running_session은 실제 달린 추천 경로와도 연결되어야 한다.

동일한 추천 경로를 여러 번 다시 달릴 수 있기 때문에 관계는 다음과 같이 보았다.

* route_recommendation 1 : N running_session

## 7. route_requests와 route_recommendation

`route_requests`는 사용자가 한 번 경로 추천을 요청한 정보를 나타낸다.

하나의 사용자 요청으로 알고리즘이 여러 후보 경로를 생성하기 때문에 관계는 다음과 같다.

* route_requests 1 : N route_recommendation

route_requests 내부의 세부 조건은 아직 알고리즘이 완전히 정의되지 않았기 때문에 지금 확정하지 않는다.

현재는 다음 정도만 둔다.

* idx
* user_idx
* prompt
* element_conditions
* selected_recommendation_idx
* created_at

`element_conditions`는 임시로 JSON을 사용할 수 있고, 추후 알고리즘 입력 규격이 정해지면 실제 컬럼 또는 JSON 구조를 확정하기로 하였다.

`route_recommendation`은 단순 점수가 아니라 알고리즘이 만들어낸 완성된 후보 경로 하나를 의미한다.

따라서 선택되기 전부터 다음과 같은 값이 필요하다.

* score
* total_distance
* total_ascent
* geometry
* route_point들

## 8. route_choice 제거 논의

초기에는 별도로 `route_choice` 테이블이 있었다.

구조는 다음과 같았다.

* route_requests
* route_recommendation
* route_choice
* running_session

하지만 route_choice에 있던 거리, 상승 고도, score, geometry 등은 실제로 사용자가 선택하기 전부터 route_recommendation에 존재해야 하는 데이터라는 점을 확인하였다.

결국 route_choice가 실질적으로 하는 일은 “여러 recommendation 중 무엇을 사용자가 선택했는가”를 나타내는 것뿐이었다.

따라서 현재 규모에서는 별도의 route_choice 테이블을 제거하는 방향으로 정리하였다.

사용자가 선택한 경로는:

`route_requests.selected_recommendation_idx`

로 표현한다.

선택하기 전에는 NULL이고, 후보를 선택하면 해당 recommendation의 idx가 들어간다.

running_session 역시 route_choice 대신 직접 `route_recommendation_idx`를 참조한다.

이렇게 하면 동일 recommendation을 여러 번 다시 달리는 것도 가능하다.

단, 향후 사용자가 선택한 이력 자체를 여러 번 저장하거나, 선택 이후 원본 경로를 수정하여 별도의 경로로 관리해야 하는 요구가 생기면 route_choice 또는 별도의 선택 경로 테이블이 다시 필요할 수 있다는 점도 확인하였다.

## 9. GIS / PostGIS / Geometry

GIS는 Geographic Information System의 약자로, RunStop에서는 지도상의 위치와 공간 관계를 처리하는 기술 영역으로 이해하였다.

현재 프로젝트에서는 PostgreSQL에 PostGIS Extension을 추가해 사용하는 방향이다.

PostGIS를 사용하면 PostgreSQL에서 공간 데이터를 저장하고 공간 Query를 수행할 수 있다.

Point, LineString, Polygon은 자동으로 생성되는 컬럼이 아니라 PostGIS에서 사용할 수 있는 Geometry 종류이다.

RunStop에서는 우선 다음 두 가지를 중요하게 사용한다.

* Point
* LineString

`route_recommendation.geometry`는 전체 추천 경로를 저장하는 LineString으로 사용한다.

예상 타입은:

`geometry(LineString, 4326)`

이다.

route_point는 기존에 latitude / longitude를 각각 저장하는 방식에서 PostGIS Point 하나로 저장하는 방향으로 변경하였다.

예상 타입은:

`geometry(Point, 4326)`

이다.

EPSG:4326은 GPS 위경도 기반 좌표계를 사용할 때 우선 고려하는 좌표계로 정리하였다.

## 10. route_point 역할

`route_point`는 전체 경로의 모든 GPS 좌표를 각각 저장하는 테이블이 아니다.

전체 경로의 세밀한 좌표는 `route_recommendation.geometry`의 LineString 안에 저장한다.

route_point는 해당 경로에서 의미 있는 주요 지점을 저장한다.

예를 들면:

* START
* WAYPOINT
* END

등이다.

주요 컬럼은 다음과 같이 정리하였다.

* idx
* route_recommendation_idx
* sequence
* title
* point_type
* elevation
* point

관계는 다음과 같다.

* route_recommendation 1 : N route_point

같은 recommendation 안에서는 sequence를 사용하여 주요 지점의 순서를 관리한다.

## 11. 현재까지 정리된 주요 DB 관계

### 약 16:29 이후까지 논의

현재 논의 결과의 핵심 관계는 다음과 같다.

users

* 1 : N user_auths
* 1 : N running_goal
* 1 : N route_requests
* 1 : N running_session

route_requests

* 1 : N route_recommendation
* selected_recommendation_idx를 통해 하나의 선택된 후보를 가질 수 있음

route_recommendation

* N : 1 route_requests
* 1 : N route_point
* 1 : N running_session
* 전체 경로를 LineString으로 보유

running_session

* N : 1 users
* N : 1 route_recommendation
* 1 : N running_trackpoint

현재 DB에서는 user_profile과 route_choice를 제거하는 방향으로 정리하였다.

Google OAuth 단일 로그인, 목표 상태 관리, PostGIS 기반 경로 및 Point 저장, 실제 러닝 세션과 GPS Snapshot 기록까지가 현재까지 논의된 주요 정책이다.

아직 확정하지 않은 영역은 경로 알고리즘의 구체적인 입력값, route_requests의 세부 조건 컬럼, 경험치 계산 공식, 레벨별 목표 거리 및 보상 정책 등이며, 이 부분은 알고리즘 및 서비스 정책이 더 구체화된 이후 결정하기로 하였다.
