``````md
# 1. 경로 생성 계층 — 현재 상태

경로 생성은 단순 최단거리 탐색이 아니라 **사용자 선호와 요구조건이 이미 반영된 Weighted Dijkstra**다.

`requirements`는 edge를 지나가도 되는지를 결정한다. 현재 대표적으로 `no_stairs`, `max_slope`가 edge-level hard constraint로 적용된다.

`weights`는 지나갈 수 있는 edge 중 어느 길을 더 선호할지 결정한다. 현재 경로 생성 단계에서는 대략 다음 요소들이 사용된다.

| 요소           | G에서 보는 데이터                                  | 현재 의미           |
| ------------ | ------------------------------------------- | --------------- |
| distance     | `edge.length`                               | 기본 이동 비용        |
| elevation    | `grade / grade_abs`                         | 경사 penalty      |
| safety/night | `lit`                                       | 야간 조명 여부        |
| nature/park  | `leisure`, `natural`, `landuse`, `waterway` | 자연환경 여부         |
| surface      | `highway`, `surface`                        | 보행 친화/큰길/비포장    |
| flow         | node의 `highway`                             | 신호등/횡단보도        |
| overlap      | `used_edges`                                | 이미 지나간 길 재사용 억제 |

사용자 weight `0~5`는 `0~1`로 정규화된다. 각 penalty도 대체로 `0~1` 범위가 되도록 설계되어 있고, 여기에 고정된 `FEATURE_COST_SCALE`이 곱해진다.

현재 주요 고정값은 대략 다음과 같다.

```text
elevation scale = 1.2
safety scale    = 0.8
nature scale    = 0.6
surface scale   = 0.8
flow scale      = 0.5

좋은 경사 = 2%
나쁜 경사 = 10%

LOOP reuse factor = 5
ONE_WAY factor     = 2
VIA factor         = 3
```

이 숫자들은 사용자 선호가 아니라 **알고리즘 튜닝값**이고, 사용자는 그 위에 weight로 중요도를 조절하는 구조다.

### `_build()`와 `_route_chain()`

`_build()`는 route mode를 이해한다.

```text
ROUND_TRIP
→ S → waypoint
→ 같은 길 역순 복귀

LOOP
→ S → waypoint
→ 기존 edge에 penalty
→ 다른 길로 S 복귀

ONE_WAY
→ S → ellipse waypoint → E
```

반면 `_route_chain()`은 mode를 모르고, 여러 anchor를 순서대로 shortest path로 연결한다.

```text
A → B → C → D
```

그래서 주로 `via` 처리에 사용된다.

현재는 `LOOP + via`와 `ROUND_TRIP + via`가 사실상 같은 순환 경로 생성 방식으로 처리된다.

### 거리 보정

현재는 waypoint의 `scale`을 조절하면서 목표 거리를 맞춘다.

```text
새 scale
=
기존 scale × target_distance / actual_distance
```

최대 6번 반복하고, 그동안 가장 오차가 적었던 경로를 보관한다.

이 방식은 간단하고 MVP에서는 충분하지만, 도로 그래프는 연속함수가 아니기 때문에 반드시 수렴한다고 보장할 수는 없다.

# 2. 피처링 계층 — 현재 상태

피처링은 경로 생성보다 구조는 단순하다. 핵심은:

> **이미 생성된 경로를 여러 데이터 소스로 측정해서 raw feature를 cand에 추가하는 것**

이다.

현재 `pipeline.py`에서는 다음 네 가지가 붙는다.

```python
c["slope"]
c["facilities"]
c["nature"]
c["surface"]
```

### slope

입력은 `cand["coords"]`와 DEM이다.

DEM은 **Digital Elevation Model, 수치표고모델**이며 각 좌표의 절대 고도를 제공한다.

현재 약 30m 간격으로 경로를 샘플링하고 각 구간에서:

```text
경사도(%) = |고도차| / 이동거리 × 100
```

을 계산한다.

현재 생성되는 값은:

```text
avg_slope_pct
max_slope_pct
elevation_gain_m
sample_count
```

이다.

현재 `elevation_gain_m`은 **오르막일 때만 고도차를 누적**한다.

### facilities

입력은 `cand["coords"]`와 하나의 통합 시설 CSV다.

현재 사용하는 유형은 화장실, 편의점, 도시공원, 가로등, 보안등, 보행등, CCTV 정도다.

경로를 EPSG:5179 LineString으로 바꾸고 주변 buffer 안의 시설을 계산한다.

각 시설마다:

```text
count
per_km
nearest_m
```

을 만든다.

현재 프로젝트 규모에서는 하나의 통합 CSV로 충분하고, 시설별 상세 속성까지 확장할 필요는 낮다고 판단했다.

### nature

입력은 `cand["coords"]`와 공원/하천 GeoJSON이다.

경로 주변 buffer와 polygon의 교집합 면적을 계산해:

```text
park_ratio
water_ratio
```

를 만든다.

시설과 다르게 “이용 가능한가”보다 **경로 주변 환경 중 자연이 얼마나 차지하는가**를 측정하는 feature다.

### surface

입력은 `cand["nodes"]`와 `G`다.

외부 파일을 보는 것이 아니라 실제 지나간 OSM edge/node를 다시 분석한다.

현재 생성되는 값은:

```text
walkable_ratio
bigroad_ratio
stairs_count
signal_per_km
crossing_per_km
length_m
```

정도다.

`surface`라는 이름은 다소 좁은 표현이지만, 현재는 코드 이름을 유지하고 문서에서 “도로 환경 프로파일”이라고 보충 설명하는 방향으로 생각 중이다.

# 현재 확인된 피처링 개선 예정

다음 변경에서는 크게 세 가지가 우선순위가 높다.

첫째, elevation feature를 조금 확장한다.

```text
기존
avg_slope_pct
max_slope_pct
elevation_gain_m

추가 후보
slope_std_pct
elevation_loss_m
elevation_range_m
net_elevation_change_m
```

여기서 특히 `slope_std_pct`는 유용하다. 절대 고도의 표준편차보다 **경사가 얼마나 들쭉날쭉한지**가 러닝 난이도에 더 직접적인 의미가 있다.

둘째, 현재 시설과 자연환경이 공통으로 쓰는 `BUFFER_M=100`을 분리하는 방향이다.

```text
FACILITY_BUFFER_M
NATURE_BUFFER_M
```

형태로 만들고, 초기값은 둘 다 약 `50m` 정도로 시작하는 방향을 고려하고 있다. 이후 실제 서울 경로 시각화로 조정한다.

셋째, 거리 계산을 통일한다.

현재:

```text
cand["actual_distance_m"]
facilities["route_length_km"]
surface["length_m"]
```

처럼 같은 경로 길이를 여러 모듈에서 다시 계산하고 있다.

앞으로는:

```text
cand["actual_distance_m"]
```

를 **canonical distance**로 두고, 나머지는 이를 전달받아 사용하는 방향이 더 적절하다.

# 3. 사용자 기본 선호 — 변경 예정

환경변수 ON/OFF 방식보다는 프로젝트 규모를 고려해 **가상의 초기 사용자 집단이 이미 존재한다고 가정하는 prior 방식**으로 가는 방향이다.

예를 들어:

```text
가상 사용자 수 = 1000
초기 평균 weight = 3.0
```

이라고 하면 실제 데이터가 들어올 때:

```text
new mean
=
(1000 × initial_mean + 실제 사용자 값의 합)
/
(1000 + 실제 사용자 수)
```

로 계산한다.

이 방식에서는 “중앙값”이 아니라 **초기 평균 / prior mean**이라고 표현하는 것이 정확하다.

추후 개인 사용자의 선호는 별도로 EMA 등을 사용해서 천천히 개인화할 수 있다.

# 4. 거리 보정 — 변경 후보

현재는 매번:

```text
scale *= target / actual
```

로 전체 비율을 그대로 반영한다.

향후에는 초반에는 크게 움직이고, 반복될수록 보정 폭을 줄이는 damping 방식이 후보가 될 수 있다.

예:

```text
scale *= (target / actual) ^ alpha
```

에서:

```text
1회차 alpha = 1.0
2회차 alpha = 0.7
3회차 alpha = 0.5
...
```

처럼 적용하는 방식이다.

아직 변경 전이며, 현재 상태 문서에는 기존 방식을 그대로 기록하는 게 맞다.

# 5. ONE_WAY 타원 waypoint — 현재 유지

현재 ONE_WAY는 start/end를 초점으로 하는 타원 위의 점을 waypoint로 사용한다.

현재 방식은 일부 타원점에서 목적지를 지나쳤다가 다시 돌아오는 형태가 생길 가능성이 있고, `bearing`과 타원의 parameter angle도 완전히 같은 개념은 아니다.

개선 후보로는 start-end 선분에 수직한 측면 영역의 waypoint만 사용하는 방법 등이 있지만, 이 부분은 **당장은 유지하고 이후 원리를 더 분석한 뒤 수정하기로 했다.**

# 6. 점수화 계층 — 현재 구조 / 상세 튜닝은 예정

현재 점수화는:

```text
Raw Feature
↓
0~100 Sub-score
↓
사용자 weights로 가중평균
↓
condition_score
```

구조다.

예를 들어:

```text
distance_error_pct
→ distance score

elevation_gain_m / km
→ elevation score

toilet_count / nearest
→ toilet score

park_ratio
→ park score

walkable_ratio
→ surface score

signal_per_km
→ flow score
```

처럼 서로 단위가 다른 raw feature를 공통 `0~100` 범위의 **적합도 점수**로 변환한다.

현재 weighting 상수들은 대부분 초기 휴리스틱이다.

```text
거리 오차 10% → 0점
상승고도 30m/km → 0점
화장실 2개 → 개수점 만점
편의점 3개 → 개수점 만점
공원/하천 ratio 15% → 100점
조명 120/km → 100점
CCTV 15/km → 100점
신호등 4/km → 0점
overlap 0.30 → 0점
pace fallback = 6분/km
```

`_DEFAULT_W`도 현재는 사용자 weight가 없을 때의 임시 fallback이다.

이 부분은 **다음 단계에서 실제 후보 경로 feature 분포를 보고 기준값을 재설계하는 방향**으로 남겨둔다.

---

```text
``````
