# RunStop 서버 아키텍처 설계 과정 중간정리

> 프로젝트 방향: **이식성이 좋고 팀원이 쉽게 실행·확장할 수 있는 서버 구조를 먼저 만든 뒤 실제 기능을 채워 넣는 방식**

---

## 1. 현재 프로젝트 아키텍처 방향

현재 RunStop은 다음 구조를 기준으로 설계 중이다.

```text
React Native
    ↓ HTTP / JSON
Node.js + TypeScript Backend
    ├─ PostgreSQL + PostGIS
    └─ FastAPI Routing Worker
            ↓
        algorithm
            ↓
        features
            ↓
        ranking
            ↓
        AI inference
            ↓
           Top 3
```

Docker 기준으로는 다음 3개 서비스를 독립적으로 둔다.

```text
docker-compose
├─ backend
│  └─ Node.js + TypeScript
├─ routing-worker
│  └─ Python + FastAPI
└─ database
   └─ PostgreSQL + PostGIS
```

React Native는 Docker Compose로 서비스하지 않고 모바일 앱으로 별도 빌드/배포한다.

---

## 2. 현재 가장 중요하게 보는 개발 원칙

기능 구현부터 바로 들어가기보다 다음 순서를 우선한다.

```text
Dockerfile / docker-compose
        ↓
환경변수 규격
        ↓
DB migration / seed / import
        ↓
프로젝트 폴더 구조
        ↓
DTO / interface
        ↓
Repository / Adapter
        ↓
Worker 연결
        ↓
실제 서비스 로직
```

핵심 목표는 다음과 같다.

- 팀원이 clone 후 비슷한 환경에서 실행할 수 있도록 한다.
- 실행 환경 차이로 인한 문제를 줄인다.
- 프론트 / 백엔드 / Python / DB를 마지막에 한 번에 합치지 않는다.
- 작은 단위로 통합 테스트한다.
- 아직 확정되지 않은 인터페이스는 억지로 완성하지 않고 열어둔다.

## 3. 인증 정책 변경

기존에는 Google OAuth 단일 로그인을 고려했지만 현재는 폐기했다.

현재 방향:

- 자체 회원가입
- 자체 로그인
- JWT 기반 인증
- bcrypt 비밀번호 해싱
- 필요 시 전화번호 인증
- OAuth 계정 병합 정책은 만들지 않음

추가 후보:

- `express-rate-limit`
- JWT rotation key
- SOLAPI / CoolSMS

JWT rotation key는 아키텍처가 커질 수 있어 아직 보류 상태이다.

## 5. TypeScript 패키지 타입 처리

모든 npm 패키지에 `@types/...`를 설치하는 것은 아니다.

판단 기준:

```text
패키지 자체에 .d.ts / types 필드 존재
→ @types 불필요

자체 타입 없음 + DefinitelyTyped 존재
→ @types/<package> 설치
```

예:

```bash
npm install express
npm install -D @types/express
```

반면 `zod`처럼 자체 TypeScript 타입이 포함된 패키지는 별도 `@types`가 필요 없다.

## 7. package.json에서 이해한 핵심

예상 scripts:

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts",
    "build": "tsc",
    "start": "node dist/server.js",
    "typecheck": "tsc --noEmit"
  }
}
```

각 역할:

```text
npm run dev
→ tsx로 TypeScript 직접 실행
→ watch 모드

npm run build
→ tsc 실행
→ src/*.ts → dist/*.js

npm start
→ 이미 빌드된 dist/server.js 실행

npm run typecheck
→ JS 생성 없이 타입 검사
```

터미널 직접 실행:

```bash
npx tsx watch src/server.ts
```

`package.json` scripts 안에서는 로컬 `node_modules/.bin`이 자동으로 잡히므로 `npx`가 없어도 된다.

## 8. tsconfig.json에서 이해한 핵심

주요 옵션:

```text
rootDir
→ TypeScript 소스 기준 폴더

outDir
→ 빌드된 JavaScript 출력 폴더

module: NodeNext
→ Node ESM/CommonJS 규칙에 맞게 모듈 처리

moduleResolution: NodeNext
→ import 경로를 Node 방식에 맞춰 해석

target
→ 출력 JavaScript 버전

lib
→ 존재한다고 가정할 표준 API

types: ["node"]
→ process, Buffer 등 Node 타입 사용

strict: true
→ 엄격한 타입 검사

sourceMap
→ dist JS와 원본 TS 위치 연결

include / exclude
→ 컴파일 대상과 제외 대상
```

VS Code는 TypeScript Language Service를 이용해 실시간 타입 검사와 경고를 제공하고, 실제 빌드 기준은 `tsc`이다.

### ESM + NodeNext 주의점

실제 파일:

```text
src/server.ts
src/foo.ts
```

여도 다음과 같이 작성할 수 있다.

```ts
import { foo } from "./foo.js";
```

빌드 후 실제 Node가 실행하는 파일이 `.js`이기 때문이다.

## 10. 환경변수 구조

환경은 3개로 나누는 방향을 고려 중이다.

```text
development
test
production
```

파일:

```text
.env.development
.env.test
.env.production
.env.example
```

`.env.example`은 실행용이 아니라 팀원에게 필요한 환경변수 목록을 보여주는 템플릿이다.

예:

```env
NODE_ENV=
PORT=
JWT_SECRET=

WORKER_URL=
DATABASE_URL=

POSTGRES_DB=
POSTGRES_USER=
POSTGRES_PASSWORD=
```

실제 값이 있는 `.env.*`는 Git에 올리지 않는 방향이다.

### 현재 환경변수 위치

공식 환경변수 기준은 프로젝트 루트로 잡는다.

```text
MidProject/
├─ .env.development
├─ .env.test
├─ .env.production
├─ backend/
├─ routing-worker/
└─ docker-compose.yml
```

Node / Python 폴더별로 `.env`를 중복 생성하는 것은 일단 지양한다.

개별 서비스의 로컬 테스트가 필요하면 다음과 같은 개인용 파일은 가능하다.

```text
backend/.env.local
routing-worker/.env.local
```

단 Git에는 올리지 않는다.

## 11. Docker 네트워크와 localhost 차이

Docker Compose 내부에서는 `localhost`가 다른 컨테이너를 의미하지 않는다.

컨테이너 내부의 `localhost`:

```text
현재 컨테이너 자기 자신
```

따라서 Docker Compose 내부 통신:

```text
backend → database:5432
backend → routing-worker:8000
```

Docker 환경 예:

```env
DATABASE_URL=postgresql://postgres:1234@database:5432/runstop
WORKER_URL=http://routing-worker:8000
```

로컬 직접 실행 환경:

```env
DATABASE_URL=postgresql://postgres:1234@localhost:5432/runstop
WORKER_URL=http://localhost:8000
```

같은 `.env`에서 같은 변수명을 두 번 선언하면 마지막 값이 적용되므로 Docker용/로컬용을 동시에 활성화하면 안 된다.

## 15. Python Worker 구조 결정 과정

초기 후보:

### A. Node가 Python을 child_process로 실행

```text
Node Container
├─ Node
└─ Python Worker
```

장점:

- 처음 연결이 단순함

단점:

- Node 이미지 안에 Python까지 포함
- 런타임 강결합
- Worker만 독립적으로 재시작하기 어려움
- Worker scale out이 불편함

### B. Python Worker를 독립 서비스로 실행

```text
docker-compose
├─ backend
├─ routing-worker
└─ database
```

장점:

- Node/Python 런타임 분리
- Worker 독립 재시작 가능
- Worker 개수만 늘릴 수 있음
- 추후 ECS/Kubernetes 등 확장 가능

현재 결정:

> Python Worker는 독립 서비스로 운영한다.

## 16. Node ↔ Python 통신 방식 결정

후보:

```text
child_process stdin/stdout
HTTP
RabbitMQ
Raw TCP Socket
```

### RabbitMQ

장점:
- Worker 구조에는 적합

단점:
- 현재 프로젝트에서는 운영 인프라가 과함

### Raw TCP

겉보기에는 단순하지만 직접 처리할 요소가 많다.

```text
message framing
requestId
reconnect
timeout
partial packet
concurrency
worker failure
```

### HTTP

장점:

```text
JSON
status code
timeout
health check
debugging
FastAPI docs
```

등 기본 규약이 이미 존재한다.

현재 선택:

> Node ↔ Python은 FastAPI 기반 내부 HTTP 통신으로 간다.

FastAPI는 외부 사용자용 메인 API 서버가 아니라 Node와 Python 사이의 내부 인터페이스로 본다.

## 17. Worker Scaling 방향

처음부터 여러 Worker를 띄우지는 않는다.

```text
Worker 1개
→ API / DTO 규격 확정
→ CPU / 처리시간 측정
→ 필요하면 Worker N개
```

경로 알고리즘 등은 CPU-bound일 가능성이 있어 Python thread보다 process 기반 확장을 먼저 고려한다.

향후 가능 구조:

```text
FastAPI Worker process 여러 개
또는
routing-worker container 여러 개
```

Docker Compose 자체는 본격적인 autoscaler가 아니므로 자동 스케일링은 이후 AWS ECS / Kubernetes 등의 영역으로 본다.

현재 프로젝트에서는 autoscaling 구현까지 필수는 아니다.

## 18. docker-compose 현재 방향

기본 구조:

```yaml
services:
  backend:
    build:
      context: ./backend
    env_file:
      - .env.development
    ports:
      - "3000:3000"
    depends_on:
      - database
      - routing-worker

  routing-worker:
    build:
      context: ./routing-worker
    env_file:
      - .env.development
    ports:
      - "8000:8000"

  database:
    image: postgis/postgis:17-3.5
    env_file:
      - .env.development
    ports:
      - "5432:5432"
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:
```

### 중요한 판단

`routing-worker`의:

```yaml
ports:
  - "8000:8000"
```

은 개발 중 FastAPI `/docs`, `/health`를 직접 확인하기 위해 사용할 수 있다.

배포에서는 Node만 Worker를 호출한다면 host port mapping을 제거할 수 있다.

Docker network 내부 통신에는 `ports`가 없어도 된다.

### depends_on

`depends_on`은 서비스 시작 순서를 관리하는 수준이다.

DB가 실제 요청을 받을 준비가 끝났는지는 보장하지 않는다.

추후:

```text
healthcheck
readiness
depends_on condition
```

등을 공부해서 추가할 예정이다.

보다는:

```text
.env.production
```

## 20. Node Dockerfile

현재 기본 형태:

```dockerfile
FROM node:24.18.0

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build

EXPOSE 3000

CMD ["npm", "start"]
```

의미:

```text
FROM
→ 사용할 기반 이미지

WORKDIR
→ 이후 명령의 컨테이너 내부 작업 경로

COPY package*.json ./
→ package.json / package-lock.json 복사

RUN npm ci
→ lock 기준으로 dependency 설치

COPY . .
→ backend 소스 복사

RUN npm run build
→ TypeScript build

EXPOSE 3000
→ 컨테이너가 3000 포트를 사용한다는 명시

CMD ["npm", "start"]
→ 컨테이너 실행 시 기본 명령
```

`EXPOSE`는 실제 port forwarding이 아니다.

실제 port mapping:

```yaml
ports:
  - "3000:3000"
```

## 22. Docker Layer / Cache

다음 순서는 의도적이다.

```dockerfile
COPY package*.json ./
RUN npm ci

COPY . .
```

이유:

- package.json / package-lock.json은 자주 바뀌지 않음
- 소스코드는 자주 바뀜
- dependency 설치는 비용이 큼

`server.ts`만 수정했을 때 기존 `npm ci` Layer를 재사용할 수 있다.

반대로:

```dockerfile
COPY . .
RUN npm ci
```

로 작성하면 소스 한 글자만 수정해도 `npm ci`가 다시 실행될 가능성이 높다.

핵심:

> 잘 안 바뀌고 비용이 큰 작업을 Dockerfile 앞쪽에 둔다.

## 26. DB Migration / Seed / Import 방향

아직 본격 구현 전이다.

### Migration

DB 구조 변경 이력을 코드로 관리하는 개념으로 이해했다.

예:

```text
001_create_users
002_create_running_goal
003_add_email_to_users
```

새 환경:

```text
DB 생성
→ migration
→ seed
→ CSV/SHP import
```

### Seed

서비스 시작에 필요한 기본 데이터 삽입.

### Import

CSV / SHP 등을 DB에 적재.

### 멱등성

같은 seed/import를 여러 번 실행해도 중복되거나 상태가 망가지지 않는 성질.

후보:

```text
UNIQUE
UPSERT
INSERT ... ON CONFLICT
```

예상 폴더:

```text
infra/
└─ db/
   ├─ migrations/
   ├─ seeds/
   └─ imports/
```

Migration 도구는 아직 결정하지 않았다.

## 27. DTO / Repository / Adapter 방향

Backend 예상 구조:

```text
backend/
└─ src/
   ├─ server.ts
   ├─ routes/
   ├─ services/
   ├─ repositories/
   ├─ adapters/
   ├─ dto/
   ├─ config/
   └─ middleware/
```

### DTO

- 확정 가능한 필드는 미리 정의
- 아직 불확실한 요소는 optional 또는 별도 타입으로 열어둠
- 구현 과정에서 확정

### Repository

- DB 접근 로직을 서비스 로직과 분리
- PostGIS 함수 사용도 이 계층에서 감쌀 가능성 있음

### Adapter

외부 서비스:

```text
TmapClient
SmsClient
LlmClient
```

등을 감싼다.

후보 경로:

```text
src/adapters/
src/adapters/external/
```

목적:

- 외부 API 교체 가능
- Mock 구현 가능
- 서비스 로직이 HTTP 세부 구현을 몰라도 됨

## 30. 현재까지의 핵심 판단

### 1. 실행 환경을 먼저 만든다

기능보다 Docker / 환경변수 / DB / 인터페이스를 먼저 고정한다.

### 2. Node와 Python을 분리한다

Node는 서비스 API / 인증 / 흐름 제어를 담당한다.

Python은 경로 알고리즘 / Feature / AI ranking을 담당한다.

### 3. Python Worker는 독립 서비스로 둔다

Node child process보다 독립 컨테이너가 이식성 및 확장성 면에서 낫다고 판단했다.

### 4. Node ↔ Python은 HTTP로 통신한다

Raw TCP보다 구현 비용이 낮고 FastAPI를 이용하면 테스트가 쉽다.

### 5. 환경변수는 루트를 기준으로 관리한다

중복 `.env`로 인한 설정 drift를 줄인다.

### 6. Docker Compose는 최종 통합 실행 기준이다

단, 개발 중 모든 작업을 Docker 안에서만 하지는 않는다.

```text
개발
→ npm run dev / uvicorn 직접 실행

통합 확인
→ docker compose up
```

### 7. Worker scaling은 나중에 결정한다

Worker 1개로 인터페이스와 기능부터 확정한다.

### 8. PostGIS는 공식 이미지를 사용한다

```text
postgis/postgis:17-3.5
```

별도 DB Dockerfile은 현재 필요하지 않다.
