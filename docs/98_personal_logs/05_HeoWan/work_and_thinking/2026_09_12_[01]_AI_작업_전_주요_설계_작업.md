## 0. 지금까지 결정한 이유

현재 AI 모델 자체는 아직 확정되지 않았지만, 모델이 무엇이 되더라도 최종적으로는 **후보 경로를 사용자에게 적합한 순서로 정렬하고 Top-K를 반환하는 Ranking 문제**라는 점은 변하지 않는다.

따라서 모델 구현을 기다리기보다 먼저 다음을 정리했다.

- 합성 사용자와 정답(Ground Truth)을 어떤 형태로 만들지
- 모델이 달라도 동일한 기준으로 비교할 수 있는 평가 구조
- 실제 서비스에서 Node / FastAPI / DB가 어떤 책임을 가질지
- 나중에 AI를 추가해도 배포 구조를 다시 뒤엎지 않도록 배포 형태를 먼저 고정

특히 `condition_score`는 **Baseline**으로 남기고, 합성 정답은 이를 그대로 복제하지 않도록 별도의 사용자 성향 기반 Utility를 만들어야 한다.

# 1. Synthetic Data / Ground Truth 설계

## 목표

합성 사용자마다 일관된 성향을 만들고, 각 요청에서 생성된 후보군에 대해 **사용자별 Utility와 Ground Truth Ranking**을 생성한다.

## 기본 흐름

```text
Synthetic User Profile
        +
Request
        +
CandidateRoute Raw Features
        ↓
사용자별 선택 규칙
        ↓
Utility
        ↓
Ground Truth Ranking
```

## 결정 사항

- `recommend()`의 응답에 존재하는 정량 Feature를 정답 생성의 주요 입력으로 사용한다.
- `condition_score` 자체를 정답으로 사용하지 않는다.
  - 그대로 사용하면 AI가 기존 휴리스틱을 복제하는 문제가 생긴다.
- 사용자별 성향에 따라 동일 후보도 Utility가 다르게 나오게 만든다.
- 가능하면 후보별 다음 정보를 남긴다.
  - `utility`
  - `ground_truth_rank`
  - `selected`
- 학습/평가용 Candidate Pool은 가능하면 일정한 크기로 맞춘다.
  - 우선 8~10개 생성 시도
  - 충분하지 않으면 생성 파라미터를 조정
  - 평가용 데이터는 일정 후보 수를 확보한 요청 위주로 사용
- 실제 지도를 직접 보는 평가는 자동 정답 생성을 대체하지 않고 **Human Evaluation / 외부 검증**으로 별도 수행한다.

## 남아 있는 OPEN

**Utility 함수가 실제 사용자 만족을 충분히 표현한다고 말할 수 있는 근거를 어떻게 만들 것인가.**

이 부분은 사용자 프로필/선택 데이터 생성 담당 결과를 받은 뒤 최종 확정한다.

# 2. AI Experiment / Evaluation Harness

## 목표

모델 종류와 하이퍼파라미터가 달라도 **동일 데이터, 동일 Split, 동일 Metric**으로 자동 비교할 수 있게 한다.

## 공통 출력 규격

모델 내부 구현과 관계없이 최종적으로 다음 형태로 변환한다.

```text
candidate_id
model_score
model_rank
```

## 평가 기준

### Baseline

```text
condition_score DESC
```

### Primary Metric

```text
HitRate@3
```

- 실제로 사용자가 선택할 후보가 AI의 Top 3 안에 들어왔는지 평가
- 서비스의 `후보 N개 → Top 3 추천` 목적과 가장 직접적으로 연결

### Secondary Metrics

```text
NDCG@3
MRR
Top-1 Accuracy
```

- **NDCG@3**: Top 3의 구성과 순서 품질
- **MRR**: 실제 선택 후보를 얼마나 앞에 배치했는지
- **Top-1 Accuracy**: 모델 1위 후보와 실제 선택 후보가 정확히 일치하는 비율

### 추가 평가

- Baseline 대비 Improvement
- Warm-start 평가
  - 학습에 등장한 사용자의 이후 요청
- Cold-start 평가
  - 학습에 등장하지 않은 사용자의 요청
- 95% Confidence Interval
- Human Evaluation

## 실험 자동화 방향

YAML 기반의 얇은 Experiment Harness를 만든다.

예상 구조:

```text
ai/
├─ configs/
├─ src/
│  ├─ dataset.py
│  ├─ splits.py
│  ├─ models.py
│  ├─ train.py
│  ├─ metrics.py
│  └─ evaluate.py
├─ scripts/
│  └─ generate_synthetic.py
└─ artifacts/
```

한 번 실행하면 다음이 자동 생성되는 것을 목표로 한다.

```text
config.yaml
metrics.json
predictions.parquet
report.md
plots/
```

즉 모델을 많이 실험하더라도 **평가 리포트 작성 방식은 항상 동일하게 유지**한다.

# 3. Service Integration 설계

## 목표

AI를 붙이더라도 기존 경로 생성 알고리즘과 서버 구조를 최대한 유지한다.

## 목표 흐름

```text
React Native
    ↓
Node
    ├─ 사용자 Profile 조회
    ├─ 이전 선택 기록 조회
    ├─ History 통계 생성
    ↓
FastAPI
    ↓
기존 Candidate Generation
    ↓
select_candidates_with_ai(...)
    ↓
Ranking
    ↓
Top 3
    ↓
Node
    ↓
DB 저장 / Front 반환
```

## 변경 예상 지점

### Node

- 사용자 Profile 조회
- 이전 선택 기록 조회
- 이전 선택 기록을 고정 길이 통계 Feature로 변환
  - 최근 N회 평균
  - 평균 경사
  - 평균 공원 비율
  - 평균 거리 오차
  - 선택 횟수
  - 필요시 EWMA
- FastAPI Request DTO에 `userContext` 추가
- 전체 후보 / Top 3 저장 정책 결정

### FastAPI

DB 직접 접근은 하지 않는다.

입력:

```text
user_profile
history_summary
weights
requirements
current_request
```

을 받아 기존 경로 생성 후 AI Ranking에 사용한다.

예상 함수:

```python
def select_candidates_with_ai(
    candidates,
    weights,
    requirements,
    user_context,
    top_k,
):
    ...
```

### DB / 학습 데이터

- 운영 DB에는 기존 컬럼을 유지
- 유동적인 Candidate Feature는 JSONB 사용
- 학습 전용 `utility`, `ground_truth_rank`는 운영 DB에 억지로 추가하지 않고 별도 Dataset 파일로 관리하는 방향 우선
- `.txt`보다 `Parquet` 또는 `JSONL` 우선 검토

## 적용 시점

현재 서버를 다른 작업자가 수정 중이므로 **지금 바로 코드를 변경하지 않는다.**

안정화 버전이 넘어온 뒤 DTO / DB / Node Service / FastAPI Input을 한 번에 변경해 충돌을 줄인다.

# 4. Deployment — 내일 최우선 작업

## 목표

AI가 아직 완성되지 않아도 현재 서비스 구조를 외부 공인망에서 실행 가능한 상태로 만든다.

나중에 모델 파일과 AI inference 코드만 교체하면 되도록 배포 기반을 먼저 완성한다.

## 목표 아키텍처

```text
React Native / Admin Web
        ↓ HTTPS
Domain
        ↓
EC2
        ↓
Caddy
        ↓
Docker Network
├─ Node Backend
├─ FastAPI Routing Worker
└─ PostgreSQL + PostGIS
```

## 내일 작업 순서

### 1. Production 환경변수 정리

```text
.env.production
```

검토 대상:

```text
NODE_ENV
PORT
LOG_LEVEL
DATABASE_URL
POSTGRES_*
JWT_SECRET
WORKER_URL
LLM / OpenAI 관련 환경변수
```

AI 모델은 나중에 필요하면:

```text
MODEL_PATH
```

같은 환경변수로 교체 가능하게 만든다.

### 2. Docker Compose Production 형태 점검

- Node / FastAPI / PostgreSQL 정상 기동
- DB Volume 유지
- `restart` 정책
- healthcheck
- 내부 Docker Network 통신 확인

외부 공개 대상:

```text
80
443
```

내부 전용:

```text
3000
8000
5432
```

### 3. DB 재현 가능성 확인

빈 DB에서:

```text
migration
→ 필요한 schema/table 생성
```

이 가능한지 확인한다.

데모 데이터 이동이 필요하면:

```text
pg_dump
pg_restore
```

를 사용한다.

Migration / Seed / Dump의 역할은 분리한다.

### 4. EC2 + Domain + HTTPS

- EC2 생성
- Security Group 설정
- Domain → EC2 Public IP 연결
- Caddy 설치/구성
- Let's Encrypt 인증서 발급
- HTTPS Reverse Proxy 구성

### 5. 외부 통신 Smoke Test

최종적으로 노트북 Wi-Fi가 아닌 **휴대폰 LTE/5G**에서도 API 호출이 되는지 확인한다.

확인 대상:

```text
/health
인증 API
/routes/recommend
```

가능하면 테스트 절차와 명령어까지 문서화한다.
